# Configure the AskerDo contract

## 1. Work out the starting point

1. Resolve the data directory: `$CLAUDE_PLUGIN_DATA` if set AND its final path segment starts with `askerdo` (the variable can leak from other plugins' contexts into the session shell), else `~/.claude/plugins/data/askerdo-askerdo`. If `config.json` is absent there, check the other `askerdo*` dirs under `~/.claude/plugins/data/` before treating the plugin as unconfigured (the harness names the dir inconsistently across session contexts) and use the dir that holds one. Read `config.json` and use it as the starting point.
2. If no config exists, the starting point is `DEFAULT_CONFIG` in `${CLAUDE_PLUGIN_ROOT}/lib/node-helpers.mjs`.

To change one setting, point the user at the Settings tab in the AskerDo pane (`/askerdo pane`, then Settings): every setting with what it does, where its value comes from and a chip to choose where to set it, saving through `askerdo settings set`; in a terminal, `askerdo settings` lists them and `askerdo settings set <key> <value>` changes one. This skill is the way to set up from scratch and to join a board.

Every write here goes through the same verb, `node "${CLAUDE_PLUGIN_ROOT}/bin/askerdo.mjs" settings set <key> <value>` (`settings set` below), one key per run: `contract.<option>` for a contract option (`contract.forecast`, `contract.dlg`, `contract.custom`, `contract.alias`, and so on) and `queue` for the queue. A toggle takes `on` or `off`, a choice its word, `contract.custom` a JSON list of strings, and the alias its text. Each write saves the value and regenerates the style; a refused value says why and writes nothing. For a board user each contract write lands on their profile on the board first, and a refused or unreachable board writes nothing. The verb never touches `boardUrl` or `boardToken`, and never prints a token.

A board user's options live on their AskerDo profile, the one held on `default` on the board, and `config.json` is this PC's copy: the join and each session start bring them from the board, and each `settings set` puts a value there first. So a PC joining a board it already has (the join-a-pc card, or the user says this PC goes on their board) goes to step 5's join first, and the interview follows only if the user wants something changed or the join said the board holds no options yet.

For a user with no board, options pasted as JSON (another PC's `config.json`, so this PC matches it) take the place of the interview; on a PC with no config and no board, mention this before starting the interview. Write each pasted option with `settings set`, skipping a `name` key, which is not a setting, and `boardUrl` and `boardToken`: never take those two from a paste (a device token belongs to the PC it was issued to, and step 5 gets this PC its own). Never print a token. Then run `node "${CLAUDE_PLUGIN_ROOT}/hooks/sync.mjs" --install`, report what it printed, and go to step 5.

## 2. The in-session interview

3. Walk the user through the choices, showing current values, batched into few questions and honoring the CURRENT dialog policy while asking:
   - Eleven booleans: `weather` (effort-mood cluster slot), `forecast` (will-you-be-needed slot plus footer anchors), `tasks` (glyph-led progress lists), `docs` (surface pointer to the shipped capability docs), `fold` (must-read separator), `decision` (decision tables), `diff` (diff fences), `emdash` (em/en-dash ban), `visual` (diagrams and charts), `interactive` (widgets and forms), `ids` (IDs carry their short human names, so a bare number never forces a scroll-back).
   - `dlg`: `blockers` | `free` | `ban` (AskUserQuestion dialog policy; a `ban` is enforced live by this plugin's PreToolUse hook).
   - `custom` (array of strings), asked only when `config.json` holds no `boardToken`: a board user's own rules are rule lines on their AskerDo profile, which ride every session and agent on every PC, so point them at `node ~/.claude/askerdo/cli.mjs profile rule-add <profile> <slug> --text "..."` and `profile show-effective --rules` instead. When a board user's `config.json` still holds `custom` rules (saved before the join), offer to move them onto their profile: list them numbered and move only the ones the user says yes to, since nothing moves without it. The profile is the one held on `default` (`node ~/.claude/askerdo/cli.mjs profile list` names it, and a save's line names it too). For each yes run `node ~/.claude/askerdo/cli.mjs profile rule-add <profile> <slug> --text "<the rule>"`, the slug made from the rule's own words (lowercase letters, digits and dashes, at most 40); a rule over 400 characters is refused there, so say so and keep it. Then write `contract.custom` as step 4 says with only the rules not moved left in it: a declined rule stays there and still rides the contract. For a user with no board: the user's own rules, each one entry, written in markdown. List the current ones numbered so they can be added to, edited, or removed by number, and say that they continue the generated rules as first-class numbered rules. Keep each one verbatim: only trailing whitespace is trimmed, the em/en-dash ban is never applied to them, and they are the right home for anything personal, because they live in `config.json` and so survive plugin updates. They shape Claude Code only; the claude.ai chat text stays generated.
   - `alias` (string, default empty): a second name for the mod's `/askerdo` command, which the mod registers at session start (and after `/clear`) to do exactly what `/askerdo` does. A bare command word: lowercase letters, digits and hyphens, starting with a letter or digit, no slash, at most 16 characters; empty means none. Not part of the contract, so the output style does not change. If a built-in, a skill or another plugin holds the word, the mod reports it once and `/askerdo` keeps working. Ask only if the user wants one. Its commands: `/askerdo` alone, `/askerdo 106b [note]`, `home`, `questions`, `pane`, `board`, `track`, `park`, `handoff`, `resume`, and `guard [on | off]` (the subagent depth guard for the project, through the `guard-on` and `guard-off` profiles; not a saved option, so never part of this interview).
4. Write each answer that differs from the saved value with `settings set` (`contract.custom` as a JSON list, `[]` for none; the queue is step 5's). When the board refuses or cannot be reached it says why and writes nothing, so tell the user and stop there. Then run: `node "${CLAUDE_PLUGIN_ROOT}/hooks/sync.mjs" --install`. `settings set` never touches `settings.json`, so this is what sets `"outputStyle": "askerdo"` in `~/.claude/settings.json` (every other setting preserved, a backup copy taken first: `settings.json.bak`, or the next free `.bak1` when one is already there; the install line names it). Report what it printed and read back the saved choices (`node "${CLAUDE_PLUGIN_ROOT}/bin/askerdo.mjs" settings`). Then go to step 5.

## 3. Choose the board (no token yet)

5. When `config.json` holds a `boardToken`, this PC is on a board: skip this step. Otherwise ask one question with three answers, honoring the dialog policy:
   - **A board on this PC**: for someone who uses AskerDo on this PC alone. It answers only this PC, copies itself daily, and moves onto a server later with `askerdo board move`. The pick unless the user said they use more than one PC.
   - **A Docker board**, on this PC or another machine: one board for several PCs. The pick for a user with more than one PC.
   - **Join a board I have**: a board another PC or a server already runs.

   On every path, when `config.json` already holds options (toggles, custom rules), ask one question first: if the board holds no reply options yet, should this PC's saved options go on it, for every PC that joins? Add `--seed` to the path's `board here` or `join` only on that yes; a board that already holds options brings them over this PC's, and `--seed` never overwrites them. Once a path has put this PC on a board, run `node "${CLAUDE_PLUGIN_ROOT}/hooks/sync.mjs" --install`, which writes the launcher and starts this PC's local server and tray now rather than at the next session start, and report what it printed. When the board said it holds no options yet, run the interview: each `settings set` puts its value on the board. Never print a token, and never take one from a paste.

   **No board.** When the user declines a board, or a path below falls through and they want neither of the others, say in one line what they go without: the band's answer chips, tracks and handoffs, profiles, and the rules in force. Then ask `text` (questions in a session-scoped file in the project, answered by typing; the default) or `off` (the classic restated footer with waiting counts), and write it with `settings set queue <value>`.

   **A board on this PC.** Check Node first: `node -e "require('node:sqlite')"`. When that fails, say the board needs Node 24 or later (`node --version` names this one) and offer a Docker board or a join instead. Otherwise ask where the daily copies go: beside the database (the default, under `~/.claude/askerdo/board-host/`, 30 kept) or a folder the user names, for example one a sync service copies off this PC. Then run:

   `node "${CLAUDE_PLUGIN_ROOT}/bin/askerdo.mjs" board here`

   It creates the board's database under the AskerDo store folder, has this PC's local server start it on `127.0.0.1` and keep it running, and saves its address, this PC's token and `queue: hub`. It refuses, writing nothing, on a PC already on a board or a Node that cannot host one, and says why. Report what it printed. For a named folder, run `node "${CLAUDE_PLUGIN_ROOT}/bin/askerdo.mjs" settings set boardBackups "<folder>"`; a folder this PC cannot write is refused, so say why and keep the default. Tell the user `askerdo backup` takes a copy now and `askerdo restore` lists the copies and puts one back.

   **A Docker board on this PC.** Run `docker version`; when it fails or shows no Server section, say Docker's engine is not running here and offer the other two paths. Otherwise check the port is free with `node -e "require('net').connect(17480, 'localhost').once('connect', () => process.exit(1)).once('error', () => process.exit(0))"` (exit 1 means something answers there: offer another, for example 17481, and check it the same way), and confirm the time zone, this PC's by default: `node -e "console.log(Intl.DateTimeFormat().resolvedOptions().timeZone)"`. On the user's yes, run with the port and zone filled in:

   `ASKERDO_PORT=<port> ASKERDO_TZ=<zone> docker compose -f "${CLAUDE_PLUGIN_ROOT}/compose.yaml" up -d --build`

   It builds the board's image from the plugin folder and starts the container `askerdo`, which restarts with Docker, with its database on the Docker volumes `askerdo-data` and `askerdo-backups`, which outlive the plugin folder. Wait for it to answer: `node -e "let n = 0; (function t() { fetch('http://localhost:<port>/health').then((r) => process.exit(r.ok ? 0 : 1), () => (++n < 60 ? setTimeout(t, 1000) : process.exit(1))); })()"`; on exit 1, show the last lines of `docker logs askerdo` and stop. Take the code from the last `setup code:` line of `docker logs askerdo`. Other PCs reach the board at this PC's network name, so join at it: take the name from `node -e "console.log(require('os').hostname())"` and check `http://<name>:<port>/health` answers with the same `fetch` check (no retries); when it does not, use `localhost` in its place. Then run:

   `node "${CLAUDE_PLUGIN_ROOT}/bin/askerdo.mjs" join http://<name>:<port> <code>`

   Then run `node "${CLAUDE_PLUGIN_ROOT}/bin/askerdo.mjs" settings set boardContainer askerdo`, so this PC's first session start of each day backs the board up inside its container (into the `askerdo-backups` volume, 30 kept); a day Docker or the container is not running goes without a copy, with a line in the log. Tell the user that the board is backed up daily that way, that the same compose line, with the same port and zone, rebuilds the board after a plugin update, and that other PCs join it at `http://<name>:<port>` with a join code minted here (`join-code` and the tray's Add a PC print this PC's network name); when another PC cannot reach it, this PC's firewall must let the port in.

   **A Docker board on another machine.** Ask the port (17480 by default), the Docker host's time zone (this PC's by default, as above) and a folder for the kit (by default a new `askerdo-board` folder under the user's home; it must be new or empty). Run:

   `node "${CLAUDE_PLUGIN_ROOT}/server/cli.mjs" kit "<folder>" --port <port> --tz <zone>`

   and report what it printed. Tell the user to copy the folder to a local disk of the Docker host (never a network share, nor Unraid's `/mnt/user`), run `docker compose up -d --build` in it, and then `docker compose logs board` for the setup code; on an Unraid host, also `chown -R 99:100 data backups` in that folder after the first start, so the appdata share can edit them. The kit's `README.txt` says the same. Ask for the board's address (`http://<host>:<port>`) and the code, check it answers with `node -e "fetch('<board address>/health').then((r) => process.exit(r.ok ? 0 : 1), () => process.exit(1))"` (exit 1: a wrong address, or the board is not up yet), then run:

   `node "${CLAUDE_PLUGIN_ROOT}/bin/askerdo.mjs" join <board address> <code>`

   **Join a board I have.** Ask for the board address (`http://<server>:17480` for a default install) and a code. The first PC on a new board uses the setup code the board prints at each start while no PC is on it (`docker logs askerdo` on a Docker board, and `docker exec askerdo node /app/server/cli.mjs setup-code` prints a fresh one). Every later PC uses a join code minted on a PC already on the board with `node ~/.claude/askerdo/cli.mjs join-code` or its tray's Add a PC (both print the address and the code); a join code expires in ten minutes, so ask for it only when ready to use it. Then run:

   `node "${CLAUDE_PLUGIN_ROOT}/bin/askerdo.mjs" join <board address> <code>`

   adding `--device <name>` when this PC's board name should differ from its host name (a code minted with `--device <name>` takes only that name). A name already on the board is refused, unless the code was minted for it, which replaces that device (a rejoin): on that refusal ask for another name and run the join again with the same code, which the refusal did not spend. A refused code (mistyped, used, expired or replaced) needs a fresh one.

   The fallback, for a first PC whose board already holds a device token minted with `token new <device>` on the board box (a board holding a token prints no setup code): ask for that token and run `node "${CLAUDE_PLUGIN_ROOT}/bin/askerdo.mjs" join <board address> --token <token>`. A refused token or an unreachable board saves nothing.

   Every join saves `boardUrl`, this PC's own `boardToken` and `queue: hub` into `config.json`, then the options on the user's profile over the saved ones (keeping any the profile does not set), and prints the device it joined as and whether the options came from the board, never the token.

## 4. Finish, whichever path was used

6. Tell the user the style takes effect in the next session or after `/clear`, so this session still answers in the old shape.
7. Run: `node "${CLAUDE_PLUGIN_ROOT}/hooks/sync.mjs" --chat-prefs`, show the output in a fenced block, and tell the user to paste it into claude.ai Settings, personal preferences (skippable; the export is also saved as `claude-chat-preferences.md` in the data directory, and later syncs will nudge when it drifts).
8. Confirm by answering in the newly configured format with a one-line sample, noting that it is hand-written until the style loads next session.
