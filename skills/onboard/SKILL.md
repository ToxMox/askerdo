# Onboard a project onto the board

Run this in a session opened on the project. The aim: after the go, a session here learns the project's rules, its open work, the user's rulings and its routines from AskerDo alone. It runs small by default:

- **Only what is live moves**: the instruction files and the rules they carry, the rule files and what loads them, the routines in use (a skill or command whose scripts history shows touched), open work, the user's rulings in their own words, memory feedback.
- **What the code tells is not recorded.** A record earns its place only where the code cannot tell: something that looks wrong but is deliberate, a trap in the tooling. Those carry the `oddity` label, so a later session keeps or drops them as one group.
- **History leaves whole.** Logs, state notes, findings, maps and finished plans go with their folder, behind one pointer record per workstream naming the commit that holds them. They are never read clause by clause for what they once said.
- **The user rules by group**: a count, three examples and one answer that keeps, drops or converts the whole group. No agent rules on entries for them.
- **One rehearsal and one go.** The rehearsal writes to a scratch board, reads it back and runs the undo, so the undo is proven before the go. The go lands the board write and one commit in the repo.
- **Depth is the user's to ask for**: folder evidence, keep reasons rechecked each run, the full repoint of cites in every file, the word checks as waits, and one fresh reader pass.

The judgment lives in the card `onboard-a-project` (`${CLAUDE_PLUGIN_ROOT}/docs/procedures/onboard-a-project.md`): read its step 3 (what moves, what the code tells, history, groups, the homes, the gaps, what is out of scope) and step 4 (the proposal's fields) before you write the proposal. The run ends with its report recorded (step 13), a run that stops early included.

The helpers are in `${CLAUDE_PLUGIN_ROOT}/skills/onboard/` (`H` below), run with the plugin's own Node; every board call goes through `~/.claude/askerdo/cli.mjs` (`--cli <path>` on `survey.mjs` and `apply.mjs` for another). `<work>` is the work folder the survey names (`<data dir>/onboard/<slug>` unless `--work`); `<own id>` is your session id. Name items, groups and folders plainly ("the deploy notes rule"), never with an id shaped like the board's (Q, T-, K-, TR-, WS-, P-). A project the board already holds (a workstream naming it, records from an earlier import) goes to `/askerdo:doctor` instead.

## 1. Tell the shape, then gather the facts

1. In a few lines, before anything runs: the aim in one line; what moves (each piece of live state to its home: rule lines on the project's profile, decisions with the user's words, cards for the routines in use, tasks with their track and handoff, the few facts the code cannot tell); what goes (each old workflow folder and the hooks, menus and servers that loaded it, in one commit, with git keeping the history behind a pointer record); what it asks of the user (one band question per group or call only they can make, then one go after the rehearsal covering the board write and the commit, or "ask me per file"); that the Claude memory folder is moved aside on their yes, never deleted; and that depth is theirs to ask for. Offer a short tour of the board in one line, built from `${CLAUDE_PLUGIN_ROOT}/docs/askerdo-quick.md`.
2. Run `node "$H/survey.mjs" <project dir>` (with `--depth` only on the user's ask). It judges nothing and writes nothing in the project: `<work>/facts.json` holds the project (its `head` is the commit the history pointers name), the instruction files Claude reads by the Project instructions setting (`instructions`) with a ledger per file clause by clause (`claude`), the rule files with what loads each and their gone or moved cites (`ruleFiles`), the routines (`routines`: each skill and command with its scripts, its commits and `recent`, the commits in the last 60 days), every folder with its file count and last touch, the memory files, the board's records for the project, and the conversion map of earlier runs (`conversion`: sources marked `unchanged`, `changed`, `removed`, `retired`, `outside` or `seeded`, folder ends, answered calls). The card's step 2 says what each fact is for and what `--depth` adds.

## 2. Judge, group, write the proposal

3. Read the facts, then open only what a judgment needs; on a project with a conversion map, only what it marks `changed`, `new` or `removed`. Judge by the card's step 3. For a large project, split the reading among helper agents by folder group, each handed the card's step 3 and writing its part in the proposal's shape; merge the parts into one proposal.
4. Write `<work>/proposal.json` by the card's step 4: `items` (each with `kind`, `source` and `text`; the plan derives an id and title left out), `folders` with their `end`, `why` and, for one that belongs to another of the project's board workstreams, `workstream`, the `claude` ledger with a fate for every clause of each instruction file, and `calls`. Write no item for the history that leaves: the plan writes its pointer record per workstream from the folders that leave and the facts' `project.head`. Group what is alike (a history folder, a rule file's rules, a set of skills, a plan's open tasks) into a group call: `{ id, ask, count, examples, items, folders, pick }`, answered `keep`, `drop` or `convert`. A private source and anything else only the user can decide is a call of its own.
5. Run the plan once (step 6's command): it refuses while calls wait and lists each group with its count and examples. Each call goes to the band as one question through your `ask` tool (else the CLI's `register`), your pick marked, its gist saying what the group is (its count, three examples, its paths), who reads it and what each answer changes in the repo and on the board. Write each answer into the call's `answer`.

## 3. Plan, rehearse, go

6. Run `node "$H/plan.mjs" <work> --session <own id>`. It applies each answer, writes `<work>/plan.json` and prints what waits on you and what it only warns about (the card's step 5). It refuses while a call has no answer, on facts gathered before the work folder's last write, undo or handover (run the survey again), and while an undo is part way. Settle each wait in the proposal and run it again until nothing waits; a warning is written as it stands. Tell the user the "dropped" lines (an edge, a supersede, a track, a gate or an unpark event naming a record no step writes), the "Rule lines go to profile" lines and the "History pointers" line (one per workstream: the folders it names and the commit that holds them, or the amend of one an earlier run wrote).
7. Rehearse on a fresh scratch file board: `node "$H/apply.mjs" <work> --board file:<scratchpad>/onboard-<slug>-1.db`. It writes in one process listing each refusal, reads the write back with coverage, runs the undo with its one press (a stand-in for the user's Withdraw), and writes `<work>/rehearsal.md`: the counts written and dropped by group, the group answers, the history pointers, how many of the records the write made the undo took back, the coverage table, what the handover's one commit does with each folder, the links the plan dropped, the refusals. Fix a refusal, a gap or a record the undo left, and rehearse again under a new file name. Nothing touches the repo or the live board.
8. Give the user the path of `rehearsal.md` and, in chat, what the card's step 6 lists. Ask for one go: it covers the live write and the handover commit; "ask me per file" stays open. On the go, record it: `node "$H/plan.mjs" <work> --go --session <own id>`.

## 4. The write and the handover, on that go

9. `node "$H/apply.mjs" <work> --board live`. It refuses without the recorded go, pauses this PC's notifications while it writes, labels every record `import:<slug>` with the ref `onboard:<item id>`, keeps each step in `<work>/manifest.json` for the undo, puts each source, each call's answer and the run on the project's conversion map, stops at the first refusal and resumes from its results when run again. Then `node "$H/apply.mjs" <work> --coverage`: each converted source read against what it became, and each file a session loads that goes read whole unless a group answer ended its folder. It exits 2 on a gap; fix the gap where it lies (`knowledge amend`, a card edit, `override request --kind fix`) and run it again, or give a block no item names its item, then the survey, the plan with the go, the write and coverage again. A gap holds back its folder.
10. `node "$H/apply.mjs" <work> --handover`, in one commit: the cards, the kept files' line edits, each instruction file rewritten from its ledger with one AskerDo section in the file the plan names (never a new instruction file), the repoint of cites in the files a session reads (instruction files, procedure cards, and the skills, commands, agents and rules under `.claude/` and `.agents/`), then each folder that passes its gate deleted, moved, retired with its settings entries, or pointed at its card, with the `.gitignore` lines that un-ignore only it. Cites in code and other documents stay as written: git and the history pointer answer them. Last, `proc scan` records the commit as each card's verified commit. Anything refused puts every edit back and commits nothing. It writes `<work>/report.md` (the counts by kind and by group, the group answers, the commit, the undo command, the deviations); tell the user the commit. "Ask me per file": `--handover --file <path>` after each OK, one commit per run. Claude's memory folder for the project (`~/.claude/projects/<the project's folder slug>/memory`): on the user's yes, rename it `memory.retired-<date>`, never delete it.
11. A fresh reader runs only on the user's ask: `node "$H/apply.mjs" <work> --reader` writes `<work>/reader.md` from the real tree, then dispatch one agent on the session model given only `${CLAUDE_PLUGIN_ROOT}/skills/onboard/fresh-reader.md` and that file, never the proposal. It reads once and answers by group; each group goes to the user as one call, and what they choose is fixed on their word. It never runs again to empty its list.
12. The undo: `node "$H/apply.mjs" <work> --undo` prints it; `--board live --session <own id>` runs it (`--all` for every import). It takes back the rule lines and fixes it made, a history pointer's amend by putting its old text and triggers back (once a session has read the pointer, by a fix request the user presses Fix on, then the undo again); the import's decisions and knowledge records leave by one withdraw request the user presses Withdraw on, and once that press lands, running the undo again deletes through the board's purge every record the import wrote (tasks, tracks with their handoffs, questions, the workstream, the withdrawn records), with their journals, history and activity. What it holds back it names (a task holding an open step added since, a track or workstream holding work the import did not write; such a workstream is closed). It prints `git revert <commit>` for the handover commit and runs none. A group the user drops after the write: write the drop answer into its call, run the plan again, then `node "$H/apply.mjs" <work> --undo --group <call id> --board live --session <own id>`; it takes back only that group's records by the same request and purge, and the import stays.

## 5. The run report

13. Record the run: `node ~/.claude/askerdo/cli.mjs proc ran onboard-a-project clean --note "<report>"` (or `deviated`, the note opening with one sentence naming the step that differed and how, with its outcome in the same call: `--fixed <commit>`, `--one-off "why"` or `--filed T-n`). The report is the card's step 9: `report.md`'s parts, the rehearsal's undo count, the gaps filed, the field bugs filed or "none", and the fresh reader's groups when one ran.
