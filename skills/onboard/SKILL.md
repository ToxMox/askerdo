# Onboard a project onto the board

Run this in a session opened on the project. The aim is a test: after the go, a fresh session here learns its rules, its work, its rulings, its routines and the facts written for sessions from AskerDo alone; anything the old machinery would still hand it is work left, or keeps a reason of a named shape with its evidence. The project's code and its product documents are the project, never the old way. Only live state moves; history (logs, state notes, briefs, finished plans) leaves the tree with its folder and git keeps it. The code gathers facts and runs the mechanical steps; you judge the project as a person who knows it would, whatever shape its old system has, and a fresh reader checks your judgment before the go.

The judgment lives in the card `onboard-a-project` (`${CLAUDE_PLUGIN_ROOT}/docs/procedures/onboard-a-project.md`): read its step 3 (what is the old way, placing everything with the clause as the unit, what each home carries, staleness, the reasons a keep may carry and the never-reasons, the gaps known today, what is out of scope) and step 4 (every proposal field) before you write the proposal. A well-built system the user runs every day is the main case: its quality is the reason to convert it, never to keep it. The run ends with its report recorded (step 13), a run that stops early included.

The helpers are in `${CLAUDE_PLUGIN_ROOT}/skills/onboard/` (`H` below), run with the plugin's own Node; every board call goes through `~/.claude/askerdo/cli.mjs` (`--cli <path>` on `survey.mjs` and `apply.mjs` for another). `<work>` is the work folder the survey names (`<data dir>/onboard/<slug>` unless `--work`); `<own id>` is your session id. Name items and folders plainly ("the deploy notes rule"), never with an id shaped like the board's (Q, T-, K-, TR-, WS-, P-). A project the board already holds (a workstream naming it, records from an earlier import) goes to `/askerdo:doctor` instead.

## 1. Tell the shape, then gather the facts

1. In a few lines, before anything runs: the aim in one line; what moves (each piece of live state to its home: rule lines on the project's profile, decisions and cards that keep a rule's files and commands, knowledge records, tracks with their handoff and tasks, questions); what goes (each old workflow folder and the hooks, menus and servers that loaded it, deleted in one commit each, kept with a reason, or moved); what it asks of the user (a band question for each call only they can make, then one go after the rehearsal covering the board write and every repo edit, or "ask me per file"); that the Claude memory folder is moved aside on their yes, never deleted. Offer a short tour of the board in one line, built from `${CLAUDE_PLUGIN_ROOT}/docs/askerdo-quick.md`.
2. Run `node "$H/survey.mjs" <project dir>`. It judges nothing and writes nothing in the project: `<work>/facts.json` (with `facts-board.json` and `facts-rules.json` on a large project) holds the project, the board's records for it, the conversion map of earlier runs (`conversion`: sources marked `unchanged`, `changed`, `removed`, `retired` or `seeded`, folder ends, answered calls, and `judgments`, each earlier keep or drop re-checked as `holds` or `rejudge`), the instruction files Claude reads by the Project instructions setting (`instructions`), a ledger per instruction file clause by clause (`claude`), the rule files with what loads each, their cites and the commits since (`ruleFiles`), every folder with its evidence, and the memory files. The card's step 2 says what each fact is for.

## 2. Read, judge, write the proposal

3. Read the facts, then open what a judgment needs, and on a project with a conversion map only what it marks `changed`, `new` or `removed` (a `seeded` source only for the kinds its records lack). Judge everything a session loads and every folder of the old machinery by the card's step 3. For a large project, split the reading among helper agents by folder group, each writing its part in the proposal's shape and handed the card's step 3; merge the parts into one proposal.
4. Write `<work>/proposal.json` by the card's step 4: `items` with a `source` each, `folders` with their ends (a loader's end is `retire`), the `claude` ledger, every clause of the facts' ledger (`keep`, `rule`, `drop` or `split`), `calls` only for what the user alone can decide, and on every keep or drop its `shape` and `evidence`.
5. Dormant plans: a plan whose work later commits show landed is history and goes with its folder; only the plans history cannot settle go to the user, as one call listing each with its real open count and last touch.
6. Before any call goes out, check its premise (card step 4) and run the plan once (step 7's command): it refuses while calls wait, and names each call that asks the user what the card settles, which you settle in the proposal. The rest go to the band, one question each through your `ask` tool (else the CLI's `register`), your pick marked, the gist saying what the thing is (its path, what it holds, a short quote), who reads it and what each answer changes in the repo and on the board; the report lists the calls and never stands in for them. Write each answer's letter into the call's `answer`.

## 3. Plan, rehearse, the fresh reader, go

7. Run `node "$H/plan.mjs" <work> --session <own id>`. It applies each answer, writes `<work>/plan.json` and lists what still waits on you (the card's step 5 names each wait and its way out); it refuses while a call has no answer, on facts gathered before the work folder's last write, undo or handover (run the survey again), and while an undo is part way. Settle each in the proposal and run it again until nothing waits. "Edge dropped" and "Rule lines go to profile" lines name what to tell the user.
8. Rehearse on a fresh scratch file board: `node "$H/apply.mjs" <work> --board file:<scratchpad>/onboard-<slug>-1.db`. It writes in one process, lists each refusal, runs coverage, hands the plan over on a copy of the repo against that board, and writes `<work>/rehearsal.md` and `<work>/rehearsal/<tag>-reader.md`. Fix a refusal or a gap and rehearse again under a new file name. Then the fresh reader (card step 6): one agent on the session model, given only `${CLAUDE_PLUGIN_ROOT}/skills/onboard/fresh-reader.md` and the reader file, never the proposal; judge its two lists, rehearse again when they changed the proposal and run one more fresh reader on the new copy. A keep that one still challenges converts or drops with its evidence by the same test and is rehearsed once more, never sent to the user as a call.
9. Give the user the path of `rehearsal.md` and, in chat, what the card's step 7 lists: the fresh reader's list as the check against the aim, the rewritten instruction file whole, one line per rule file, hook and server, the stale rules dropped with their evidence, the gaps filed, the counts, the folders that go and stay, what an undo cannot take back, and what a session here stops seeing and where it finds it. Ask for one go: it covers the live write and every repo edit; "ask me per file" stays open. On the go, record it: `node "$H/plan.mjs" <work> --go --session <own id>`.

## 4. The write and the handover, on that go

10. `node "$H/apply.mjs" <work> --board live`. It refuses without the recorded go, pauses this PC's notifications while it writes, labels every record `import:<slug>` with the ref `onboard:<item id>`, keeps each step in `<work>/manifest.json` for the undo, puts each source, each call's answer, the judgments and the run on the project's conversion map, stops at the first refusal and resumes from its results when run again. Report the counts from the manifest. Then `node "$H/apply.mjs" <work> --coverage`: each converted source read clause by clause against what it became, and every block of a rule file that goes named by an item; fix a gap where it lies (`knowledge amend`, a card edit, `override request --kind fix`) and run it again; a block no item names gets its item in the proposal, then the survey, the plan with the go, the write and coverage again. A gap holds back its folder's delete. Coverage puts on each source's map row the lines it read with no gap, and a later run takes only those lines as written, so the item added for a gap is written.
11. `node "$H/apply.mjs" <work> --handover`: the cards and `proc scan`, each instruction file rewritten from its ledger with one AskerDo section in the file the plan names (never a new instruction file), each loader retired with its settings entries, the repoint of cites from files that stay (a cite in running text goes where the proposal's `cites` points it, else to the card a going skill became, else takes a git note, after a markdown link rather than inside it; a relative link or `../` path is read from its file's folder, and a file name labelling a link to that file stays the label; any other cite as `cites` says, else left as it is and listed, as is a path git never held, which gets no note), then each folder that passes its gate deleted or moved in a commit of its own, with the `.gitignore` lines that un-ignore only that folder. Tell each commit as it lands. It ends by comparing the real tree with the rehearsal copy: when they differ, run the fresh reader again on the real tree before the report. "Ask me per file": `--handover --file <path>` and `--repoint --file <path>`, each after the user's OK. Claude's memory folder for the project (`~/.claude/projects/<the project's folder slug>/memory`): on the user's yes, rename it `memory.retired-<date>`, never delete it.
12. The undo: `node "$H/apply.mjs" <work> --undo` prints it; `--board live --session <own id>` runs it (`--all` for every import). It drops the tasks, tracks, questions and rule lines it wrote and closes its workstream; the import's decisions leave by one withdraw request the user allows, a knowledge record stays, and it prints `git revert <commit>` for each handover commit, running none. The import reads undone only once the user has pressed Allow or Keep on that request: run the undo again after the press. A source whose records all stay keeps its row on the conversion map, so a rerun reads it as unchanged.

## 5. The run report

13. Record the run: `node ~/.claude/askerdo/cli.mjs proc ran onboard-a-project clean --note "<report>"` (or `deviated`, the note opening with one sentence naming the step that differed and how). The report is the card's step 9: the fresh reader's last list as the check against the aim with the handover's diff, the counts, the stale drops with their evidence, the keeps with their shapes, the gaps filed, the coverage table, the handover's commits, ran clean, deviated, fixed by hand, field bugs filed or "none", and the undo command.
