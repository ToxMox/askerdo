# Onboard a project onto the board

Run this in a session opened on the project. Nothing goes on the board until the user has marked the review page (or, with no calls left, said go in chat), seen the rehearsal and said go, and nothing in the project changes until the handover, each edit on their OK. An onboarding is one arc with the user engaged: it follows the card `onboard-a-project` (`${CLAUDE_PLUGIN_ROOT}/docs/procedures/onboard-a-project.md`) and ends with its run recorded (section 11), including a run that stops early.

The helpers are in `${CLAUDE_PLUGIN_ROOT}/skills/onboard/` (`H` below) and run with the plugin's own Node. Every board call goes through the AskerDo CLI at `~/.claude/askerdo/cli.mjs`; pass `--cli <path>` to `survey.mjs` and `apply.mjs` to use another. `<own id>` is your session id, the id in the scratchpad path. Name rows by their title ("Row 12 (deploy notes)"), never with an id shaped like the board's (Q, T-, K-, TR-, WS-, P-), and name an old queue's question by its title and file, never by its old label.

## 1. Up front, before anything runs

1. Tell the user the run's shape in a few lines, before the survey:
   - **What it asks of them:** a short report of what was found; a handful of band questions, only for rows the session cannot settle from the repo; one press of I'm done on the review page when calls are left, else a go in chat; a go after the rehearsal; an OK for each repo edit at the end.
   - **The page:** every row starts at a proposal the session has already judged against the repo; they press only to disagree. There is nothing to skim.
   - **What changes at the end, each on their OK:** the state file and the old handoff files become short pointers to the board, CLAUDE.md is reworded for the board, the decision log is frozen, the old protocol's checklist is rewritten for the board, and Claude's memory folder for the project is moved aside.
   - **What the import cannot carry, and how the session covers it:** a rule text over 400 characters (the session shortens it), an ordered list's order (the session gives each task what it waits on and who runs it), and work in flight that only the state file names (the session turns its next steps into tasks).
2. Never ask the user to look at something that needs nothing from them: every ask names what they decide or press.
3. Offer a short tour of the board in one line; skip it when the user declines or already works on the board. Build it from the docs, so it matches the installed version: `${CLAUDE_PLUGIN_ROOT}/docs/askerdo-quick.md`, `docs/work-system.md` (the short version, the kinds, tracks and handoffs, knowledge, profiles) and `docs/question-hub.md` (where the board lives, registration at ask time), plus `node ~/.claude/askerdo/cli.mjs proc scan --help` for procedure cards. One or two plain sentences each on the board, workstreams, tracks and side tracks, tasks, questions, handoffs, profiles and rule lines, procedure cards and knowledge records: about fifteen lines, no ids.

## 2. The board check and the survey (read only)

4. Run `node "$H/survey.mjs" <project dir>`. It reads the board first: the workstreams that name this project (keyed by its git remote, else its folder), records from an earlier import (label `import:<slug>`, refs `onboard:<row id>`), their tracks, and the knowledge records and profiles held on the project. A failed board read is reported, not fatal. Then it reads the project and writes nothing there: handoff files (with the file AGENTS.md, CLAUDE.md or a README says to read first or keep current, taken as the state file, which the output names on its State file line) and dated series with their `git log --follow` versions, checkbox lists, decision logs (split by entry heading, or by top-level bullets that start with an entry id such as `D12.`, else, when plain top-level bullets carry the file, one row per bullet under its section heading, or, when tables carry the file, one row per table row titled by its first cell, or the next cell after an id, number or date), CLAUDE.md and AGENTS.md bullets, the Claude memory files for the project (each by its type, read at the top of the frontmatter or under `metadata:`: feedback as rule lines, reference as knowledge, user as a question of whose profile), step lists and `docs/procedures` files, an old `.claude/questions` queue (an answered question that repeats a decision-log entry is proposed left, the entry kept as the ruling), and any other dot-folder. In a git repo it also reads the newest 3000 commits, subjects and file paths only, never diffs (the output says how many it read): rulings told only in commit messages, planning, handoff, decision and TODO files deleted from the repo, the project arc (commits per top-level area and month, one knowledge row), reverts and branches left unmerged. Each find is a row with where it is (file, line, commit), its date from the old system, a proposed home and a staleness read (its last change against the project's recent activity, and whether the current state file still names it; when a guide names the state file, a recent one-version note it never names, such as a lane checkpoint, starts at Leave rather than as a call). The last line names `rows.json` in the work folder (`<work>` below), which defaults to `<data dir>/onboard/<slug>` on this PC.
5. The session's own layer is `<work>/overrides.json`, read by every survey run:
   - `include`: `[{ "path": "notes/STATUS.md", "as": "handoff" }]` (or `"decisions"`) for files the patterns missed;
   - `exclude`: globs to leave out;
   - `rows`: `{ "<row id>": { patch } }`: a row's new `home`, `title`, `fields`, starting mark `def` (`keep` or `leave`) and `why`, `"call": true` for a row only the user can settle (`"call": false` clears it; `"pair": "<row id>"` shows the call beside that row), `"converted": true` once a Convert is reworked (with `"choice": "leave"` when the rework is to leave it). A patch reaches every row, the surveyed ones and those added through `add`; the survey warns about a patch whose id matches no row, naming it;
   - `add`: whole rows. A task row may carry `fields.track` (the track row it goes on), `fields.after` (row ids, T-n ids, or a number naming the n-th task row on the same track, 1 first), `fields.before` and `fields.runBy` (`orchestrator`, `fork` or `agent:<model>`): the plan lays them out on the track so the ready set follows the order. A question row may carry `fields.track` (the track row it belongs to, or a TR-n) and `fields.gates` (the task rows it blocks, or T-n ids);
   - `workstreams`: `[{ "key": "main", "use": "WS-4" }]` to import into a workstream already on the board, or `{ "key", "name" }` for another new one.

## 3. Tell what was found, before proposing anything

6. Report plainly, in a few lines and never a table of every source and home, in this order: what the board already holds for the project; what the survey found, by source (files, memory, the old queue); the TODO comments in code (they stay in the code); what it could not place. Propose nothing yet: the homes and their counts come after the discovery pass (step 9).
7. Fit the run to the kind of project:
   - **Already on the board:** the first row imports into the workstream that holds the project, and rows an earlier import wrote drop out. When the board holds it in more than one open workstream, ask which one takes the import and name it in `workstreams`. When nothing new is left, say so and stop.
   - **A homemade system:** the patterns may miss it. Read CLAUDE.md, AGENTS.md, the README and the unplaced dot-folder rows for what the project calls its status, plan or decision files ("read STATUS.md first", a `notes/` or `.ai/` folder); add each through `include`, drop noise through `exclude`, run the survey again and report what changed.
   - **No handoff system:** the survey finds little, perhaps CLAUDE.md lines, memory files or one list. Say so; the import may be just a workstream and a few rule lines, or nothing. Never invent tracks or tasks to fill it, and offer to stop.

## 4. The discovery pass, before the page

8. Judge every row against the repo's current state, not only its kind and source, so the page reaches the user as a few real calls. A small project (a few dozen rows or commits) runs the pass inline in the session. For a large survey, split the rows by group among agents (for instance: direction and live work; lists and open questions; rulings; rule lines and knowledge; git history), each reading the repo and returning a verdict per row: stale, duplicate, superseded or live, with the evidence (a commit, a file, a newer entry).
   - Set each row's starting mark and why from its verdict in `rows` (`def`, `why`): a stale or superseded row starts at Leave, a duplicate at Leave with a why naming the row it repeats, a live one at Keep in the home that fits.
   - Shorten each rule text over 400 characters to a line of at most 400 in its own words, in `fields.text`.
   - The state file's live work: turn its next steps into task rows through `add`, in order, each with `fields.track` (the state file's track row), `fields.after` and `fields.runBy`, so the imported track shows what is ready and who runs it.
   - The git-history agent reads the `history:` rows and settles each: a call for the user, evidence on a named row (say it in that row's why), or leave. A deleted file's row names the commit holding its last version (`git show <commit>:<path>`); read it for anything that still holds. The arc row sharpens the other agents' staleness verdicts. A commit message is a claim: never promote one to a decision unless the user says so.
   - A row the pass cannot settle keeps `"call": true` and a why saying what the call is.
9. Run the survey again. Only calls go to the user's band: one question per row, or per group of rows that share an answer, its options the homes the row could take plus leave, your pick marked (the mod's `ask` tool where it runs, else `register`). Put each answer in `overrides.json` (`rows`) and run the survey again.
   - **No calls left** (the survey prints no calls line): the reply's first line says nothing here needs the user, then the import in one short count line (kept per home, left out), no table. Their go in chat stands for I'm done (step 11); the page is an optional link for anyone who wants to look.

## 5. The review page

10. Run `node "$H/render.mjs" <work>`, then start the server in the background (the shell tool's background mode): `node "$H/serve.mjs" <work> [port]`. It binds 127.0.0.1 (port 8767 unless given; a busy port says so, so pass another) and prints `review page: <url>`: give that URL as a markdown link. It serves only the page and its marks, and saves marks only from the page it served (a token written into the page each run; after a restart the page asks for a reload). The page opens on the call rows; the rest sit collapsed by group at their proposals.
11. With calls, tell the user in two lines: every row already holds a proposal, so they change only a row they disagree with (Keep, Convert with a note saying how, or Leave; the group buttons mark a whole group), the page saves as they go, and they press I'm done and tell you. When the page says its server is not running, they press Copy my choices and paste them: write that to `<work>/choices.json`.
    - With no calls, give the URL in one line as there to look at if they want, never as a review to do, and ask for their go in chat. On the go, stop the server and run `node "$H/plan.mjs" <work> --chat-go --session <own id>`: it writes `choices.json` done, keeps any marks the page saved and notes the go came from chat. It refuses while a call is unmarked. Never write `choices.json` by hand.
12. A question raised while the page is open goes to the band as in step 9; after an answer, run the survey and `render.mjs` again and tell them to reload: the marks stay, keyed by row id. When they say done, read `choices.json` (it has `"done": true`, from the page or `--chat-go`) and stop the server.

## 6. The plan

13. Rework each Convert row as its note says, in `overrides.json` (`rows`, with `"converted": true`): toward a home, or, when the note shows the row should not go in, to leave with `"choice": "leave"`. The plan honours that as a leave and `choices.json` stays as the user marked it. A note you cannot act on is a question. Run the survey again (it leaves `choices.json` alone).
14. Run `node "$H/plan.mjs" <work> --session <own id>`. It writes `<work>/plan.json` (each step one CLI call, in order) and lists the rows still waiting on you: an unreworked Convert, an unplaced row marked Keep, a rule line with no text or over 400 characters (shorten it in `rows`). Settle each, then run it again until nothing waits. An "Edge dropped" line names a task row whose after or before names no task the plan writes: fix the row or accept it.
    - Your session id names who wrote each record. The plan leaves it off `track new`, `track layout` and `handoff write`, where it would make this session hold every imported track or hand its own tasks in hand over.
    - Tasks that carry an order go onto their track with a `track layout` step after `track new` (their edges and run-by); an ordered task on no track gets `task edit --run-by` and `edge add` steps.
    - A question row with a track or gates gets a `question edit --track --add-gate` step right after it registers; questions register after the tracks and tasks they name. A "Track dropped" or "Gate dropped" line names one that is no track or task the plan writes.
    - An old queue's question is registered under its title, and a bare old label in its text becomes that question's title, since the board reads a bare Q-and-number token in prose as one of its own records; a label inside a file name passes.
    - Rule lines go to a profile named by the project's slug. When the board already has that name built in or held by anything else, the plan never writes into it: it picks a free name (`<slug>-2`) and says so on a "Rule lines go to profile" line. Tell the user which. A profile you name in `rows` (the user's answer about a memory row) is taken as named.
15. Dates: the CLI keeps each record's original `created` (workstreams, tasks, decisions, knowledge, questions, and every handoff with its commit's stamp), but stamps `updated`, `closed` (done tasks, finished tracks) and a track's own dates with today. So each record's text carries its old dates: "From the old system: file line N (commit), date (how it was dated)".

## 7. The rehearsal

16. Apply the plan to a scratch file board first, a fresh file each time (a rehearsal resumes by step from its own results file): `node "$H/apply.mjs" <work> --board file:<scratchpad>/onboard-<slug>-1.db`. It keeps going past a refusal and lists each one, makes a stand-in for each existing workstream the plan names, leaves out each existing track or task id a step names (listed under Named on the real board; the live write sends them), and keeps its handoff lists and log in a temp home, never this PC's data folder. Without `--board` it is a dry run that prints every command. A scratch board holds none of the live board's records, so a clash with one (an id-shaped token in a text) shows only on the live write.
17. Show the user the counts per kind (the Written line), each Skipped and Refused line, and the repo edits planned for after the write. Fix a refusal in `overrides.json` and the plan, and rehearse again under a new file name. Ask for their go on these counts.

## 8. The live write, only after the user's go

18. Run `node "$H/apply.mjs" <work> --board live`. It refuses while any row waits on you or `choices.json` is not marked done (by the page or the go in chat). The write runs quiet: it sets the local server's notification pause (the one the tray menu and the notifications page set) for at most an hour, and lifts it when the write ends or stops, retrying once; a pause the user had set before or changed during the write stays as it was. When the lift fails it says so with the step that lifts it (Resume now on the tray menu, or the notifications page's link): pass that to the user. The pause quiets every session's notifications on this PC, so it covers the write only. Every record it writes that can carry one (workstreams, tracks, tasks, decisions, knowledge records and questions) carries the label `import:<slug>` and the ref `onboard:<row id>`. It stops at the first refusal; fix it and run again: the steps done are skipped, and a step that started with no recorded id is never sent twice (it says how to find it on the board).
19. Report the counts, the workstream and tracks made (from the manifest), and where the manifest is.
20. When agents run the work after the write (the handover, the memory folder, any fix), take the import's own track in hand (`node ~/.claude/askerdo/cli.mjs resume <TR-n> --session <own id>`) or a task on it (`task update <T-n> --in-hand --session <own id>`), so they show on the board. Otherwise leave the track on the shelf for the user to resume.

## 9. The manifest, the undo and a rerun

21. `<work>/manifest.json` holds every id written, in order, with the call that takes it back. The undo walks it backwards: `node "$H/apply.mjs" <work> --undo` prints it; `--board live --session <own id>` runs it (`--all` for every import, not just the last).
    - **It removes** the tasks and tracks (a dropped track takes its handoffs and its edges go with its tasks), the questions it registered and the rule lines it added (the profile comes off the project first), and closes the workstream it made.
    - **Decisions and knowledge records** leave only through an override request the user allows. The undo files a withdraw request for each decision, one each since the board asks rulings alone, and says so; tell the user how many wait on their Allow or Keep. A knowledge record stays, and the undo says so: a withdraw takes only decisions and no verb removes one.
    - **It leaves, and says so:** a finished track (it stays finished, with its handoffs; its tasks are dropped), a profile's last line (a profile has to set something; no project holds it any more) and procedure cards (they follow their `docs/procedures` files).
22. A rerun on this PC proposes only what is new: the survey drops the rows the manifest holds, written or left out. The manifest lives in this PC's data folder; from another PC the survey finds what an import wrote by the `onboard:<row id>` refs on the board's `import:<slug>` records (tracks and questions included), a track with no such ref by its name, and a rule line by its slug on a profile only the project holds. Rows left out last time come back there, to be left again on the page.

## 10. The handover, each edit on the user's OK

23. `<work>/pointers.json` holds the short text each old handoff file becomes: its track, its workstream and the resume command, with the old text kept in git history. It covers every import in the manifest, so a write resumed after a stop still names the files the first run made tracks for; it is written on a stop as well, and a file already holding its pointer drops out.
24. Propose the repo edits as one list and make each on the user's OK, then commit in the project with explicit paths:
    - **The state file's hazards and running checks** move somewhere durable first (CLAUDE.md, a knowledge record or a procedure card), since the pointer replaces its text.
    - **The pointers:** write each into its file.
    - **CLAUDE.md:** reword the lines that send a session to the old files so they point at the board (the track to resume, where rulings and rule lines live). Lines a page note asked to keep stay as they are.
    - **The decision log:** frozen, with a line at its top saying new rulings go on the board.
    - **The old protocol's checklist** (a session-start or handoff routine): rewritten for the board's own verbs, or retired where the board does it.
    - **Step lists:** move each the plan names for after the write into `docs/procedures/<name>.md` and run `node ~/.claude/askerdo/cli.mjs proc scan --project <dir>`.
25. Claude's memory folder for the project (under `~/.claude/projects/<the project's folder slug>/memory`), once its rows are on the board: ask the user, and on their yes move it aside (rename it `memory.retired-<date>`), never delete it. Say the import's rule lines and knowledge records now carry it.
26. The run closes without a handoff of its own when the session holds no track it started: the imported track's latest handoff is the one to resume. A session that took the track in hand (step 20) lets it go or hands it off as its rules in force say.

## 11. The run report, at the end or at any stop

27. Record the run on the card, clean or deviated, with the report as its note: `node ~/.claude/askerdo/cli.mjs proc ran onboard-a-project clean --note "<report>"` (or `deviated`, the note opening with one sentence that names the step that differed and how, since the card's flag and draft edit carry that sentence alone). The report's sections, in order:
    - **Counts:** rows surveyed, with overrides and added rows; starting marks from the discovery pass; the user's own marks; plan steps; written, refused and left out; what landed (workstream, tracks with their handoffs, tasks, decisions, knowledge records, rule lines and profile, questions).
    - **Ran clean:** the steps that went as this skill says.
    - **Deviated:** each place the run left the skill, with its cause.
    - **Fixed by hand:** what the session did that the helpers should have.
    - **Field bugs filed:** the ids, or "none".
    - **Undo:** how many imports the manifest holds and the command that takes them back; the repo edits still waiting on the user.
28. Each thing in AskerDo that tripped the run is filed where the session's rules in force say AskerDo field bugs go (a profile rule line naming the project, workstream and label), each with what happened, the cause and a fix, after checking the open field bugs there for the same fault. With no such rule, it rides the deviated note only.
