# Doctor a project already on the board

Run this in a session opened on the project when the board already holds it: a workstream naming it, knowledge records on it, records from an earlier import, or rows on its conversion map from a run on any PC. A project with nothing on the board goes to `/askerdo:onboard`. The doctor is onboarding's engine (the same facts, proposal, plan, rehearsal, write, coverage and handover) plus the record checks below, which read the board's records for the project, never every file of the repo. It runs small by default, as onboarding does: only what a session meets is checked, alike findings go to the user as one group, and depth is the user's to ask for. Anything of the old way still in the repo is judged by the onboard card's steps 3 and 4 (`${CLAUDE_PLUGIN_ROOT}/docs/procedures/onboard-a-project.md`); read them before you write the proposal. A run follows the card `doctor-a-project` (`${CLAUDE_PLUGIN_ROOT}/docs/procedures/doctor-a-project.md`) and ends with its run recorded (step 5).

The helpers are in `${CLAUDE_PLUGIN_ROOT}/skills/doctor/` (`D`) and `${CLAUDE_PLUGIN_ROOT}/skills/onboard/` (`H`); every board call goes through `~/.claude/askerdo/cli.mjs` (`--cli <path>` on `checks.mjs` and `apply.mjs` for another). `<own id>` is your session id. Name findings plainly, never with an id shaped like the board's.

## 1. Tell the shape, then run the checks

1. In a few lines: what it checks (the rule lines in force on the project, the board's shape, the open tasks against the task shape, the cards, the repo's instruction files and rule files, the records whose source changed, then anything of the old way still in the repo, as onboarding finds it); what depth adds on their ask (knowledge records against their sources, duplicates, task rewrites, a ref and amend on each record the board already holds); what it asks of the user (one band question per group or call only they can make, then one go after the rehearsal, which covers the fixes, the board writes and the repo edits, or "ask me per file").
2. Run `node "$D/checks.mjs" <project dir> --who <the user's name>` (the name the user goes by, which the step check matches beside "the user"; `--depth` only on the user's ask). With nothing on the board for the project it prints "not on the board yet: run askerdo:onboard" and exits 1: run `/askerdo:onboard`. Otherwise it gathers onboarding's facts into the same work folder (`facts.json`, at the same depth, with the project's conversion map from the board), runs the checks and the reconcile on the board's records, and writes `<work>/checkup.json`: each finding as an item of kind `fix` with its proposed fix (`fields.fix`: the CLI call it makes and what it changes back from) and its evidence, and a call in `calls` for each finding or group only the user can settle. It prints one `Checkup:` line: the findings per check and the calls left for the user, left last time counted apart, and by default what `--depth` adds. An `Already on the board, skipped:` line names each proposal item the board holds. A check whose board reads failed has no count: the line reads `Checkup incomplete (...)`, the run exits 2, and you stop, fix the failed reads (the error names the call) and run it again; an unread check is never clean. A `This PC:` line says AskerDo's prompt hooks do not run on this PC (an organization's guard): tell the user it in the report, with what still works, as the line words it.

## 2. Judge the findings, write the proposal

3. Read each finding in `checkup.json` against the facts and what you open, and of the repo only what the facts' conversion map marks `changed`, `new` or `removed`. Write into `<work>/proposal.json` the fixes you agree with, each as it stands in `checkup.json` (its `id` names its check and target, so a rerun matches it), with the calls they bring; a group finding goes in with its one call. A finding you judge wrong stays out, with a line on why in the run report. An earlier run's proposal that was written and handed over is renamed `proposal.<its go date>.json` first. Anything of the old way still in the repo is judged by the onboard card's steps 3 and 4, as items, folders and ledger clauses in the same proposal.
4. What the checks find and the fix each proposes:
   - **Rule lines in force**, each line of a profile the project alone holds: over 400 characters or ending in a cut, reworded with your shorter words (`fields.fix.text`); citing a path the repo lacks or a folder an earlier run retired (the conversion map's folder ends), reworded to the new place when the map names one (a moved folder, the one record a source became), else your words; covered by a built-in line, cleared; differing from a decision, a call with the decision's words as the fix; on a profile others hold too, or from a ruling, a call whose pick is leave.
   - **Board shape:** an open inbox task sharing words with a live track goes to that track; the inbox tasks no track shares words with are one group call (put them all on one live track, or leave them; place one apart with its own fix); a parked track whose reason names an open task, track or question gains it as its unpark condition, else a call; an inbox-only workstream holding real work is a call; the questions long asleep with nothing set to wake them are one group call (wake them all, drop them all, or leave them).
   - **Task shape**, each open task (judge each with its block in hand, `node ~/.claude/askerdo/cli.mjs task block T-n`, several ids in one call):
     - Steps its worker may not do (`steps`): open steps naming the user, a look or sitting, real use, or a later session, merge, release, install or restart before they can be checked. Candidates only: a step its worker does stays. Each other step moves with `task update T-n --move-steps`, the list in `fields.fix.stdin` (each `{ "check": n, ... }`): `"onto": "T-m"` an open task on its track labelled `look` or `review` (the row's `onto` lists them); a new task with its place fields and `name` (at a real place on the track you hold, with its `before`, it files at once; a later session's check waits on its track for the next session as the row's `moves` drafts it; a sighting in real use, `"tier": 4` with a date `wake` in the inbox: each of these is an asked place, carrying `here`, the real place on your held track, and created only on the user's press of the placement question the move raises); or `"question": "@{<item id>}"`, a question item in the same proposal for what the user owes. The plan holds the move until the list is written.
     - A look close (`look`): `task edit T-n --add-label look --clear-close`. The look is its own question, asked by the session that runs it on its track; the doctor asks none.
     - A when close (`when`, then `when-close`): its fact goes into the description as the done clause, then the close clears; keep both rows, in that order.
     - Blocked or deferred on nothing named (`waits`): from its last note, an edge (`edge add T-n T-m --reason`), a gate (`question edit Q-n --add-gate T-n`), a wake (`task edit T-n --wake <date>` in the inbox, `--wake next-session` on a track), or a question item gating it when the user owes the answer; write `fields.fix.op` and `fields.fix.args`.
     - An unconfirmed run older than a day (`unconfirmed`): no fix; the report names the holder and its last heard, so the user resumes or confirms that session. Taking it over is the user's word.
     - An inbox task with no wake and no created stamp (`nowake`): a wake 14 days out. When its on-no-track fix is kept with a track, keep that one and judge this one wrong.
   - **Cards:** each `proc scan --check` error or warning is a repo edit you make on the go.
   - **The repo:** an instruction file's clause citing a gone file is a one-line repoint, and one citing nothing live is a repoint or a drop by the staleness test (its subject gone, or a later ruling); a rule file a session loads citing paths gone or moved is a repoint, and one citing nothing live converts or drops when its subject is gone; a Project instructions setting changed since the last run means each file Claude reads by it is judged again as onboarding judges CLAUDE.md, its ledger written in `claude`, and never a CLAUDE.md written beside an AGENTS.md Claude reads alone.
   - **Changed sources:** a mapped record whose source changed since the run that read it waits on your words: read the source against its records and amend what moved (`fields.fix` with `op`, `args` and `body`).
   - **Already on the board:** an item of the proposal at hand that the board holds (its `covered`) is skipped and named.
   - **At depth:** a task with no done clause, or whose job moved into its notes since its last rewrite (`rewrite`), takes your words: `task update T-n --description <what the work is now, ending in its done clause> --note <why>` in `fields.fix.args`. A knowledge record whose source still in the repo says more gains the missing clauses as an amend; records a newer one on the same subject holds whole are one group call (supersede each by its newer one, or leave them), and pairs that each hold clauses the other lacks are named for a merge by hand; a record with no project whose text names a repo path or the project gains the project. Each item the board already holds becomes a fix adding the ref `onboard:<item id>` to that record, with the clauses it lacks as an amend (a note on a task), so the next run skips it by that ref.

## 3. Onboard steps 5 to 12, with these differences

Follow the onboard skill from step 5 (the calls on the band) to step 12 (the undo):
- Settle each call you can from the repo or the board in its `answer`; a fix waiting on words or a pick waits in the plan until you write `fields.fix.text` or `fields.fix.args`. A group call's answer adds a fix for each of its members.
- Each call left goes out as one band question through your `ask` tool (else the CLI's `register`), only for a choice the user's wants settle, its premise checked first, its gist saying what the thing or group is (its count and three examples, its path), who reads it and what each answer changes in the repo and on the board. The report lists the calls and never stands in for them.
- The plan puts each fix after every create; a repo fix goes on the handover's list of edits you make on the go and commit on the same go.
- The rehearsal runs no fix: each is listed under the doctor's fixes in `rehearsal.md` as it will run, since it changes a record only the real board holds; the undo it proves covers the creates.
- The undo takes each fix back from what it was: old words on a rule line (a cleared line comes back), a task back on its old track or unplaced in the workstream it left with a wake 14 days out, a ref, project, label, gate or edge removed, and a woken or dropped question back asleep on the snooze it had. A history pointer's amend goes back to the text it had (by a fix request the user presses, once a session read it). A line reworded from a ruling, any other amend, a moved step, a description amend, a cleared close, a wake set on an inbox task, a park condition, a supersede and a reconcile's ref while its amend stands stay, and the undo lists them.

A rerun on a doctored project finds nothing new: each fix changes what its check reads, the import's items are held by their refs and by the conversion map, a call answered before is not asked while its subjects are unchanged, a group whose members changed is asked again, and a finding the user left (its call answered leave on the map) sits under left last time while its subjects are unchanged.

## 4. The run report

5. Record the run: `node ~/.claude/askerdo/cli.mjs proc ran doctor-a-project clean --note "<report>"` (or `deviated`, the note opening with one sentence naming the step that differed, with its outcome in the same call: `--fixed <commit>`, `--one-off "why"` or `--filed T-n`). The report: the checkup counts per check (found, fixed, judged wrong, left), left last time apart, whether it ran at depth, then onboard step 13's parts, naming the fixes the undo leaves standing.
