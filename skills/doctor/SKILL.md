# Doctor a project already on the board

Run this in a session opened on the project when the board already holds it: a workstream naming it, knowledge records on it, records from an earlier import, or rows on its conversion map from a run on any PC. A project with nothing on the board goes to `/askerdo:onboard`. The doctor is onboarding's engine: the same facts, proposal, plan, rehearsal, write, coverage and handover, plus the record checks below, which read the board's records for the project, never every file of the repo. Its aim is onboarding's: after the go, a fresh session here learns its rules, its work, its rulings, its routines and the facts written for sessions from AskerDo alone, and what the old machinery still hands it is work left or keeps a reason of a named shape with its evidence. The judgment of anything of the old way still in the repo is the onboard card's step 3 (`${CLAUDE_PLUGIN_ROOT}/docs/procedures/onboard-a-project.md`); read it before you write the proposal. A run follows the card `doctor-a-project` (`${CLAUDE_PLUGIN_ROOT}/docs/procedures/doctor-a-project.md`) and ends with its run recorded (step 5).

The helpers are in `${CLAUDE_PLUGIN_ROOT}/skills/doctor/` (`D`) and `${CLAUDE_PLUGIN_ROOT}/skills/onboard/` (`H`); every board call goes through `~/.claude/askerdo/cli.mjs` (`--cli <path>` on `checks.mjs` and `apply.mjs` for another). `<own id>` is your session id. Name findings plainly, never with an id shaped like the board's.

## 1. Tell the shape, then run the checks

1. In a few lines: what it checks (the rule lines in force on the project, the board's shape, the knowledge records against their sources, the cards, the repo's instruction files and rule files, what an earlier run kept whose evidence changed, what an earlier run left, then anything of the old way still in the repo, as onboarding finds it); what it asks of the user (a band question for each call only they can make, then one go after the rehearsal, which covers the fixes, the board writes and the repo edits the report lists, or "ask me per file"); that records the board already holds gain a ref, never a second copy.
2. Run `node "$D/checks.mjs" <project dir>`. With nothing on the board for the project it prints "not on the board yet: run askerdo:onboard" and exits 1: run `/askerdo:onboard`. Otherwise it gathers onboarding's facts into the same work folder (`facts.json`, with the project's conversion map from the board, so a run from any PC sees what both skills converted before), runs the checks and the reconcile on the board's records, and writes `<work>/checkup.json`: each finding as an item of kind `fix` with its proposed fix (`fields.fix`: the CLI call it makes and what it changes back from) and its evidence, and a call in `calls` for each finding only the user can settle. It prints one `Checkup:` line: the findings per check and the calls left for the user, left last time counted apart. A check whose board reads failed has no count: the line reads `Checkup incomplete (...)`, the run exits 2, and you stop, fix the failed reads (the error names the call) and run it again; an unread check is never clean.

## 2. Judge the findings, write the proposal

3. Read each finding in `checkup.json` against the facts and what you open, and of the repo only what the facts' conversion map marks `changed`, `new` or `removed`: what it holds `unchanged` was converted already and is never opened again, and write into `<work>/proposal.json` the fixes you agree with, each as it stands in `checkup.json` (its `id` names its check and target, so a rerun matches it), with the calls they bring; a finding you judge wrong stays out, with a line on why in the run report. An earlier run's proposal that was written and handed over is renamed `proposal.<its go date>.json` first. Anything of the old way still in the repo is judged by the onboard card's steps 3 and 4, as items, folders and ledger clauses in the same proposal, each item with its `source` and each keep or drop with its `shape` and `evidence`. A finding that waits on your judgment and carries no fix to run (a judgment to make again, the Project instructions setting changed) is answered by that judgment in the proposal, never copied in as a fix item.
4. What the checks find and the fix each proposes:
   - **Rule lines in force**, each line of a profile the project alone holds: over 400 characters or ending in a cut, reworded with your shorter words (`fields.fix.text`); citing a path the repo lacks or a folder an earlier run retired (the conversion map's folder ends), reworded to the new place when the map names one (a moved folder, the one record a source became), else your words; covered by a built-in line, cleared; differing from a decision, a call with the decision's words as the fix; on a profile others hold too, or from a ruling, a call whose pick is leave.
   - **Board shape:** an open task on no track goes to the track sharing its words, else a call listing the live tracks; a task in progress with nobody on it since before the project's recent activity goes back to open with a note; a parked track whose reason names an open task, track or question gains it as its unpark condition, else a call; an inbox-only workstream holding real work and a question long asleep are calls.
   - **Knowledge records:** a from line naming a gone file gains an amend saying where the source is now; a source that says more gains the missing clauses as an amend; two records with the same subject, the older superseded by the newer when it holds every clause, else a call; a record with no project gains it when its text names a repo path or the project. The import's own records are its output, never a finding, unless one item stands written twice (a redo after an undo): the older goes. A decision log's supersedes are yours to judge when you read a changed log: write `supersedes` on the item. **Cards:** each `proc scan --check` error is a repo edit you make on the go. **The repo:** an instruction file's clause citing a gone file is a one-line repoint, and one citing nothing live is a repoint or a drop by the staleness test (its subject gone, or a later ruling); a Project instructions setting changed since the last run means each file Claude reads by it is judged again as onboarding judges CLAUDE.md, its ledger written in `claude`, and never a CLAUDE.md written beside an AGENTS.md Claude reads alone. **What earlier runs kept:** a judgment the facts mark `rejudge` (its reader gone, its cite unresolved, its event come, its file changed, or no evidence recorded) is judged again from the facts, never copied forward and never left: convert it, drop it with its evidence, or keep it with a reason of a named shape and fresh evidence; one marked `holds` stands. A kept clause or kept file is held to the same test as a rule line: a rule file citing paths gone or moved is a repoint, and one citing nothing live is stale unless its subject is still in the tree. **Earlier runs:** each Fixed by hand or Deviated line of the last run report is a call.
   - **The conversion map:** a mapped record whose source changed since the run that read it waits on your words: read the source against its records and amend what moved; a mapped record the board no longer holds while its source stays is a call (convert it again, or leave it gone).
   - **Reconcile before create:** an item of the proposal at hand that the board already holds (its `covered`) becomes a fix adding the ref `onboard:<item id>` to that record, with the clauses it lacks as an amend (a note on a task); the next run skips it by that ref.

## 3. Onboard steps 6 to 12, with these differences

Follow the onboard skill from step 6 (the calls on the band) to step 12 (the undo):
- Settle each call you can from the repo or the board in its `answer`; a fix waiting on words or a pick waits in the plan until you write `fields.fix.text` or `fields.fix.args`. A call answered by a track's option adds the fix with that track.
- Each call left goes out as the onboard card's step 4 says: only a choice the user's wants settle, never whether a piece of the old way converts; its premise checked first; one band question through your `ask` tool (else the CLI's `register`), its gist saying what the thing is (its path, what it holds, a short quote), who reads it and what each answer changes in the repo and on the board. The report lists the calls and never stands in for them.
- The plan puts each fix after every create; a repo fix goes on the handover's list of edits you make on the go.
- The rehearsal runs no fix: each is listed under the doctor's fixes in `rehearsal.md` as it will run, an amend with its text, since it changes a record only the real board holds; its check against the aim counts the fixes apart from the old system's live state.
- The fresh reader (onboard card step 6) runs when the plan changes the repo (a rewrite, a move, a delete, a loader retiring) or when a kept reason's event has passed; otherwise the report names the last fresh read and its date. After the handover, a real tree that differs from the rehearsal copy has it read again before the report.
- The undo takes each fix back from what it was (old words, the task back unplaced with a wake 14 days out or on its old track, the status back, a ref or project removed); an amend, a supersede, a park condition and a line reworded from a ruling stay, and the undo lists them.

A rerun on a doctored project finds nothing new: each fix changes what its check reads, the import's items are held by their refs and by the conversion map, a call answered before is not asked while its subjects are unchanged, and a finding the user left (its call answered leave on the map) sits under left last time while its subjects are unchanged.

## 4. The run report

5. Record the run: `node ~/.claude/askerdo/cli.mjs proc ran doctor-a-project clean --note "<report>"` (or `deviated`, the note opening with one sentence naming the step that differed). The report: the checkup counts per check (found, fixed, judged wrong, left), left last time apart; the judgments made again and how each came out; then onboard step 13's parts (the fresh reader's list, or the date of the last one when it did not run), naming the fixes the undo leaves standing.
