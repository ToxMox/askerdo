# CLI reference

The AskerDo CLI reads and writes the board from a terminal or a script: questions, work records, tracks, settings and this PC's own setup. Sessions call it too, so everything a session does on the board you can do by hand.

## Running it

On a PC joined to a board, the session-start sync keeps a launcher at `~/.claude/askerdo/cli.mjs` that always points at the installed plugin:

```sh
node ~/.claude/askerdo/cli.mjs help
node ~/.claude/askerdo/cli.mjs list
node ~/.claude/askerdo/cli.mjs settings
```

With no board there is no launcher: change your reply options and the queue in the Settings tab of the AskerDo pane (`/askerdo pane`, then Settings), which saves through the same `settings set` the verbs marked "Works with no board" below describe. Every other verb needs a board.

## Reading an entry

Each entry below is the verb's own help, the text `askerdo help <verb>` and `askerdo <verb> --help` print:

- The first line is the call: `<...>` is a word you supply, `[<...>]` one you may leave out, `...` one or more.
- The indented line under it says what the verb does; a `stdin:` line says what it reads on standard input (a JSON payload, or text).
- Each `--flag <value>` takes a value and each bare `--flag` is a switch; `(repeatable)` flags add up across repeats, and every other flag keeps its last value.
- `--json` prints one JSON object (an array for `list`), for scripts. `--session` is the calling session's id, which sessions pass so the board knows who wrote a record; you leave it off. `--user` marks a call as your own act (a press or an answer you typed) rather than a session's: the verbs that only you may run (`override decide`, `override unscrub`) need it.

Exit codes: `0` success, `1` bad input, a board refusal or no board set, `2` any other failure. Results go to stdout and diagnostics to stderr.

When the board cannot be reached, reads come from this PC's cache with a note saying so, and writes fail plainly: nothing is queued.

The board server has its own maintenance commands (backup, export, check, tokens), run on the server itself: see [Set up a board](board-setup.md). The `/askerdo` command in a session is a different thing: see [Daily use](daily-use.md).

This page is built from the CLI's help by `node scripts/build.mjs`, so it matches the installed version.

## Questions

### register

```text
askerdo register
  register a question; left out, the track is the one the session holds and the workstream is that track's (else the in_progress tasks', else the subscribed one)
  stdin: JSON payload (docs/question-hub.md, "Registration")
  --json: print JSON
```

### answer

```text
askerdo answer <question id>
  record an answer: flip the question to answered and tell its subscribers
  --pick <value>: the option: 106b, or the bare letter b
  --note <value>: why, in words
  --session <value>: your own session id
  --user <value>: the session the user pressed a chip in: their act, told to that session too
  --version <value>: the version the card showed: one before a rewording is refused; it never amends (--amend does)
  --json: print JSON
  --amend: correct an answered question
```

### drop

```text
askerdo drop <question id>
  record a decline
  --note <value>: why
  --session <value>: your own session id
  --user <value>: the session the user pressed drop in: their act, told to that session too
  --json: print JSON
```

### snooze

```text
askerdo snooze <question id>

  --until <value>: YYYY-MM-DD
  --trigger <value>: words that wake it
  --wake-on <value>: <record id>[:<ending status>]
  --user <value>: the session the user pressed snooze in: their act, told to that session too
  --json: print JSON
```

### wake

```text
askerdo wake <question id>

```

### surface

```text
askerdo surface <question id>
  bump asked, print the payload, subscribe the session
  --session <value>: your own session id
  --json: print JSON
```

### list

```text
askerdo list
  the open questions (or --kind work records), blockers first then oldest, one head line each
  --project <value>: the project directory (scopes questions)
  --session <value>: your own session id
  --kind <value>: workstream, task or knowledge
  --workstream <value>
  --track <value>: TR-n: the questions on that track
  --status <value>
  --priority <value>
  --label <value>
  --json: questions: { questions, openSetUrl }; work kinds: an array
  --open
  --all
  --snoozed
  --blocking
  --names-line: the reply's names line for --project (default: the current directory), scoped by --session and --blocking; nothing when none is open
```

### question edit

```text
askerdo question edit <question id>
  reword an open question in place, move it between lanes, set or fix its pick, or name the tasks it gates
  stdin: with no field flag: the reworded question, a whole register payload, keeping its id (open or snoozed questions)
  --workstream <value>
  --track <value>: TR-n (an old P-n or TH-n names the track it became)
  --session <value>: your own session id
  --pick <value>: the recommended option letter (open or snoozed questions)
  --add-gate <value> (repeatable): T-n
  --remove-gate <value> (repeatable): T-n
  --json: print JSON
  --clear-workstream
  --clear-track
  --clear-pick
```

## Any record

### show

```text
askerdo show <record id>
  one record (several below --full) at a read level: the brief form by default, and the last line names what it left out and the flag that brings it back
  --journal-tail <value>: keep the last N journal notes
  --project <value>: the project slug an old brain id belongs to
  --section <value>: one section by name, such as Intent, Answer or Journal
  --session <value>: the session reading it (a read by another session makes it used)
  --json: print JSON: alone, the whole record (what scripts and the mod read); with a level, that level

  --since-resume: journal notes since the latest resume
  --head: one line each: label, name, status and what it waits on
  --full: the whole record, nothing left out
  --history: its old texts, each change with who, when and why (a profile by its name)
```

### task edit

```text
askerdo task edit <T-n id>
  flip a task's fields
  --name <value>
  --status <value>: open, in_progress, blocked, deferred, dropped or completed
  --priority <value>: high, medium or low
  --ordinal <value>
  --workstream <value>
  --plan <value>
  --serves <value>: o1,o2: the outcomes of its workstream it serves
  --run-by <value>: who runs it: orchestrator, fork or agent:<model> (agent:opus)
  --review-scope <value>: a review task reads track (its own track, the default) or project (every code task in the project since the last project-wide review)
  --close <value>: "with T-n" (it closes when T-n completes), look (it closes at the look of the user) or "when <a checkable fact>"
  --session <value>: your own session id

  --description <value>: rewrite its Description in place, on the same terms as --intent
  --track <value>: TR-n: the track it goes on
  --before <value> (repeatable): a T-n on that track that waits on it (repeatable)
  --after <value> (repeatable): a T-n on that track it waits on (repeatable)
  --unplaced <value>: why it waits on no track (the found list shows it)
  --add-label <value> (repeatable)
  --remove-label <value> (repeatable)
  --add-ref <value> (repeatable)
  --remove-ref <value> (repeatable)
  --json: print JSON
  --clear-workstream
  --clear-plan
  --clear-serves: it serves none
  --clear-run-by: nobody is named to run it
  --clear-close: it closes by hand
  --landed: a look task's work landed: the user's band offers Close
  --in-hand: with --session: this session takes it in hand (it may hold several)
```
