## 0.8.15 - 2026-11-04

- BAND CHIPS CONFIRM AND QUEUE LIKE THE CARDS. The chip's hover card says it answers or queues.

Home's map with amber beads and a review to do, the Tracks tab with its amber cells, the board's track page with a finished review and what it covered, and a new picture of a band chip's open strip; the README describes Home's map as it draws.

## 0.8.14 - 2026-11-04

- THE BOARD KNOWS WHICH FINISHED CODE A REVIEW HAS READ. The board keeps the commits each task finished with and the reviews that read them, in two tables (board migration 012) that ride the export, the import and the backups. The mod links every commit a session makes, a subagent's included and with no rules in force, to its task: a task id in the message first, then the agent's dispatched task, then the task in hand, else a guess the readout names; a commit no task owns counts as unowned project work. A handoff write and resume, and `coverage --scan`, link the commits made outside a session whose messages name a task. Only counted source makes a code task: lockfiles, generated files, Markdown, docs, fixtures and binaries never count, and the setting `review.ignore` adds a project's own globs. The verbs are `commit link`, `commit move` (relink by hand, with a reason), `review covers` (set or narrow a review's list) and `coverage <TR-n|WS-n>`, with the session tools `review_covers` and `coverage`.
- THE REVIEW STATION ON A TRACK IS THE GATE. A review task (labelled `review`, or named "Review ...") covers the uncovered code tasks on its track that finished before it started, or, with `--review-scope project` on task create, task edit or a track layout step, every code task in the project since the last project-wide review plus the commits no task owns. A track reads review due once `review.tasks` (5) finished code tasks wait unreviewed: the band draws a review due row whose press opens the Tracks tab at the track, and the kickoff, the handoff and `coverage` say the same. `review.depth` sets how much the board makes of it: `off` nothing, `light` (the default) the nudge, and `full` also reopens a completed review when work it read gains a commit or completes after it, so the tasks waiting on it wait again, and holds `track finish` until a review covers the track's finished code (`--waive "<reason>"` goes ahead and is recorded). A reopened review keeps the covers its change did not outdate, and a commit on a finished track's task reopens nothing there and waits for the next project-wide review. A built-in rule line tells sessions where review stations go: after each wave of parallel lanes, where work touched code another lane or track also touched, once five finished code tasks sit unreviewed, and before anything that ships. Configure offers the depth once on a board, and the Settings tab shows the three review settings under Tests.
- THE STATION MAP DRAWS THE WORK NO REVIEW HAS READ. Finished code tasks no review covers draw as amber beads on their track's rail between stations, on Home's Where we stand and the board's track pages. A review is a diamond: outlined while to do, amber with "N to review" when reopened, and filled grey with "N covered" once done, the beads it covered folded into it; a press on a done review lists what it covered, each a link, closed with the pane's X. A finish held for a review wears an amber padlock, unless a review planned before it is the way through, and the legend names a review mark only when the map draws it. The Tracks tab colours unreviewed done cells amber, draws the padlock on a held tile and reads "review due".
- EVERY NAME THE PANE DRAWS OPENS ITS BOARD PAGE. Track, task, question and decision names and ids in the pane and on the band's cards open their board pages: the Tracks tab's station rows, its tiles' workstream and longest chain (packed whole into two rows), its bottom line and a shut section's names; Home's map, its other workstreams, its wait lines and lines left out; the terminal's line names; the found row's ids; and the track and task hover cards with each wait.
- SETTINGS AND THE BOARD JOIN SURVIVE A PLUGIN UPDATE. This PC's files (config.json with the board address, device token and options, the handoff lists, the project map and the sync log) live in `~/.claude/askerdo/pc/`, which no plugin update, uninstall or marketplace remove reaches. The session start moves an existing plugin data folder there once, renaming config.json into place so a session starting beside it never reads half a file, and leaves the old folder for a downgrade; until the move, and on any copy failure, the old folder is read. A setting or join that a session still on an older AskerDo saves into the old folder reaches `pc/` at the next session start, and a settings copy leaves an unreadable config.json as it is. AskerDo reads the Claude app's folder from `CLAUDE_CONFIG_DIR` when it is set (the output style, settings.json, the plugins and the projects folders), while the store and `pc/` stay in `~/.claude/askerdo`.
- UPDATING A PC IS ONE COMMAND, AND THE APP CAN DO IT ON ITS OWN. `claude plugin update askerdo@askerdo` then a new session updates a PC: the update fetches the marketplace itself (read on Claude Code 2.1.304), every doc that updates a PC says so, and none removes the marketplace. Configure offers the Claude app's auto-update for AskerDo once per PC: a yes turns on `autoUpdate` on the AskerDo entry in `~/.claude/plugins/known_marketplaces.json` (the switch /plugin shows under Marketplaces) and on its `extraKnownMarketplaces` entry in `~/.claude/settings.json` when there is one, keeping every other key, which is the desktop app's way in since it has no /plugin panel. The answer is the per-PC setting `pluginUpdates` (`ask`, `on`, `off`), which the Settings tab also changes. The session start puts the switch back to the saved answer only when the app holds no value, as a marketplace remove and add leaves it, and an on or off set in /plugin becomes the saved answer.
- AN UPDATE REPLACES THE OLD LOCAL SERVER AND BRINGS THE TRAY BACK. A session start replaces an older local server of this store, ending one that will not stop through its stop route by its process id once that process is Node holding the store's port. Session starts racing after an update replace it once: a stop names the version it expects, and a current or newer AskerDo server found instead is kept. A tray closed with Exit comes back at the next session start, and the ping reports the tray as `up`, `closed` or `down`. The local server shuts down, tray included, when its store folder is deleted or its secret minted again: measured, it leaves within one watch tick and the next start brings one up. `askerdo board --restart` stops the local server and starts a fresh one on the same port, the troubleshooting page uses it, and in a session whose copy an update replaced it refuses with the fix to start a new session.
- THE TRAY RUNS FROM ITS OWN COPY IN THE STORE. The tray runs from `~/.claude/askerdo/board/tray/`, one folder per build, so a plugin reinstall never meets a locked exe in the plugin cache: measured, a marketplace remove and same-version reinstall while the tray ran from the cache left 1039 files of the old copy behind, and with the store copy the cache is left whole. The copy puts back a missing `app.ico`, and a tray run from another store's copy leaves the Start Menu link alone.
- ONE COMMAND SAYS WHAT IS WRONG ON A PC. `askerdo status` checks the store, the saved settings and board join, the board (answering, token, version), this PC's local server, the tray and whether the session runs a copy an update replaced, one line each, every problem with the command or step that fixes it; `--json` gives it as data, and it exits 1 when it lists a problem. A lost board join gets the join-code command to copy, a PC with no config.json leads with `/askerdo:configure`, a tray exe missing from this copy gets the update as its fix, settings an older session left in the plugin data folder are named, a tray switched off in the notification settings is no problem, and a PC that uses no store skips the store. A local server that does not answer its ping in time reads as busy, with the fix to check again or run `askerdo board --restart`, and `askerdo board` words that refusal the same way and never stops a server it could not identify. It runs in the asking process, so it judges that copy rather than the local server's. The troubleshooting page starts from it.
- THE BAND AND THE STATUS ROW SHOW THIS PC'S FIRST PROBLEM WITH ITS FIX. They draw the first problem `askerdo status` finds: Start or Restart runs the local server's fix in place, Copy puts the join-code command for another PC on the clipboard, and a healthy PC draws nothing. The mod looks again when a call finds the local server gone, after a fix, each minute while a problem stands and at once when `board/local.json` changes under it, running `askerdo status` once per new problem.
- A SESSION RESUMED ACROSS AN UPDATE IS TOLD WHAT TO DO. A tool call with a field name the installed AskerDo does not take is refused with the installed version and the fix to start a new session, in the mod's handoff tools, the CLI's handoff write and update and the board's handoff update. The board's refusal of a handoff key an AskerDo older than 0.8.13 sends says to update that PC with `claude plugin update askerdo@askerdo` and start a new session.
- THE NEEDS YOU FOOTER DRAWS UNDER THE QUESTION CARDS. A reply that asks pastes the question's block in its footer, under the footer's label. On the desktop the mod draws the footer under the last question card, so it is the last thing on screen however many cards the reply asks, and folds each block in it to one line naming the question and saying it is on the card above, so the reply points at the card once. The contract, the ask tool's result and description, the CLI's register result and the question file doc say so, and the golden fixtures are regenerated.
- FOUND WORK ALWAYS NAMES ITS PLACE. A task a session files names a track (with `--before` and `--after` for the steps around it) or `--unplaced` with a reason, else the filing is refused naming both ways and the board's hint, the open track sharing the most labels, files and words with it. `track found <TR-n>` lists what a track's arc filed, where each went and the command that moves it, and the handoff, the kickoff, a release's question and the Tracks tab's Found this arc row (the unplaced first) show the same. `task edit` moves a task between tracks (`--track`, `--before`, `--after`, `--unplaced`), and task create, task edit, track capture and track layout name the session from `CLAUDE_CODE_SESSION_ID` when none is passed. The mod's inbox capture and the join card's field-bug task pass their unplaced reason.
- THE STATION MAP DRAWS EVERY WAIT AS A LINE. The waits into one station share one trunk, the lines out of one station share one trunk, a wait no single gap serves turns twice along the band between two rows, and no bend crosses a station's words. A release waiting on 13 tasks draws all 13 (10 in 0.8.13). Measured on 420 seeded random tracks: drawings with a line through a station's words fall from 153 to 0, and far waits kept as words from 225 to 108.
- THE DISPATCH CHECK FLAGS ONLY A BRIEF THAT ASKS TO PIN WORDING. Its pin wording row flags a brief line asking for a test that pins exact wording, never a line about regenerating golden fixtures.
- THE LOCAL SERVER ANSWERS ONLY ITS OWN HOST NAMES. It takes `askerdo.localhost`, `localhost` and `127.0.0.1` on its port, and refuses a link carrying the older `t-ask-and-ding.localhost` host.
- THE README PRESENTS ASKERDO AS A CLAUDE MOD, AND THE GUIDE COVERS THIS RELEASE. The guide, the work system doc, the quick reference and the configure skill cover review coverage, the health row, found work, the footer under the cards and linked names. The CLI reference groups the status, board move and backup verbs, `track found`, and the commit and review verbs, and the `review.ignore` example names generic generated paths.
