## 0.8.16 - 2026-11-08

- ONBOARDING CONVERTS A PROJECT'S OLD WORKFLOW INTO ASKERDO. `/askerdo:onboard` moves the system a project worked by onto the board: rules sessions still load become rule lines, work in flight a track with its handoff and tasks, rulings decisions, open questions questions, facts knowledge records and routines procedure cards; run logs, briefs and finished plans leave with their folder and stay in git. Claude writes the plan from a survey's facts and settles what the repo or the board answers; the rest reaches the user as band questions. A rehearsal on a scratch board and a copy of the repo, read by a fresh agent, shows what will land, and one go covers the board write and every repo edit. The review page is gone. Measured on a large game project: 464 board changes, 0 refused, 0 coverage gaps over 75 sources, CLAUDE.md from 6,759 to 1,224 bytes, and an undo that gave back the exact tree.
- /ASKERDO:DOCTOR CHECKS A PROJECT ALREADY ON THE BOARD. It runs onboarding's arc on the same engine, so what is left of the old way converts in the same pass, and onboarding a project the board holds sends the user to it. It checks rule lines (too long, cut, citing a gone or retired path, covered by a built-in line, at odds with a decision), loose and stale work, knowledge records whose source is gone or says more, duplicates, procedure cards, CLAUDE.md or AGENTS.md citing nothing live, a changed Project instructions setting, kept judgments whose evidence changed, and converted records whose source changed or that the board lost. Claude judges each finding, one go runs the fixes and the undo reverses them; a failed board read exits 2, so an unread check never reads clean. `knowledge edit` takes `--add-ref`, `--remove-ref`, `--add-project` and `--remove-project` on a record in use, and `show` takes several ids.
- THE SURVEY READS GIT HISTORY AND OPENS ONLY WHAT SESSIONS LOAD. It starts from the entry points (CLAUDE.md, AGENTS.md, `.claude/rules`, Claude's memory for the project, the README, a handoff protocol's resume files, Codex's `.agents/` skills and the scripts hooks and `.mcp.json` servers run), takes one git log, one status and two grep passes, and writes `facts.json` in this PC's work folder: per folder its files, commits, first and last touch, subjects, the files citing into it and the code reading it; CLAUDE.md clause by clause; and the board's records for the project with its answered questions. It holds no reader for any particular file format. Which instruction files Claude reads follows Claude Code's Project instructions setting, so an AGENTS.md Claude reads is an instruction file like CLAUDE.md. Measured on the large project: 200 s and over 32,000 rows before, 17 s with 9 files opened and 126 KB of facts.
- CLAUDE.MD KEEPS WHAT THE PROJECT IS, AND A SCOPED RULE KEEPS ITS SCOPE. The conversion reads CLAUDE.md, or the AGENTS.md Claude reads, clause by clause: working rules go to the board, facts stay in new words, lines sending a session to a retired file come out, and one AskerDo section at the end points at the board; it never creates a CLAUDE.md that would hide an AGENTS.md. A rule scoped by `paths:`, a nested CLAUDE.md or the commands it names becomes a decision or procedure card carrying those files and commands. Hooks, menus and MCP servers that loaded the old rules retire with what they load, and a hook that enforces a rule stays as the project's tool. A folder stays only with a reason of a named kind: the product, someone else's file, a document for people, a tool, or a capability AskerDo lacks.
- THE HANDOVER COMMITS ONE FOLDER AT A TIME AND REPOINTS WHAT CITES IT. An old workflow folder is deleted in its own commit once no code reads it, coverage holds every source from it and no open item in it outlived the dormant-plans answer; a folder git does not track stays and is named, and a commit git refuses puts the folder back and stops the handover. Files that stay are repointed to the record or file that holds what they cite, else to the commit holding the old text, with links, code spans, fences and globs still working. Routines become `docs/procedures/<name>.md` cards. The write runs every board step in one process, about 11 times faster, with this PC's notifications paused while it runs.
- THE COVERAGE PASS GATES EVERY DELETE. It reads each converted source clause by clause against every record it became, wherever the item came from: table cells and numbered headings count as clauses, a word-for-word copy or a clause a procedure card carries counts as carried, and a cut counts as dropped only when its evidence backs it or its source marks it out of force. Every markdown rule file under a folder that goes, and every file a hook or server script loads, is read whole, so a rule a missed load carried is a gap, and a clause with no fate holds its file's rewrite.
- AN UNDO TAKES A CONVERSION BACK, AND A REDO WRITES NOTHING TWICE. The undo removes the import's tasks, tracks, questions and rule lines, closes the workstream it made, takes its decisions back in one withdraw request the user Allows or Keeps once, keeps knowledge records and says so, prints `git revert` for each handover commit newest first and runs none without the user's word, rewrites Codex's AGENTS.override.md and drops the conversion map's rows for the records it withdrew. It reads done only after the Allow, and the plan waits while an undo is part way. A redo writes each rule again before its folder leaves and no detail record or amend twice. Measured on the large project's copy: the redo matched the first handover's 23 commits with 0 refused and 0 gaps, and the rerun after it planned 0 steps.
- THE BOARD KEEPS A CONVERSION MAP FOR EACH PROJECT. Board migration 013 adds it: each source a run converted with its content hash and the records it became, each folder's end (deleted or moved at which commit, or kept and why), each answer the user gave and each run, carried by the export, the import and a project rename. A second onboard or doctor run, from any PC, opens only folders with commits since, new folders and changed sources, skips every unchanged item and asks no answered call again while its subject is unchanged; the handover's own rewrites never read as a change. `askerdo conversion` lists a project's map, and `conversion put` and `conversion drop` are the write's and the undo's own calls. Measured: a second run on the large project with a new session's proposal wrote 0 steps, opened nothing and asked nothing.
- HOME DRAWS A DRIFT LINE. Once per folder, after the band's first load, Home names what drifted: a path CLAUDE.md or AGENTS.md cites that is missing, a profile rule line over 400 characters or cut, a retired folder holding files again since the last conversion, and a cite into a retired path, the last two from one read of the board's conversion map. A retired cite or folder closes it with "run the doctor" and a link to the doctor card's runs once the doctor has run, else with `/askerdo:doctor`; a missing cite alone ends with `(/askerdo:doctor)`, a long rule line alone with neither; it never draws on the band. The profile setting `doctor.drift`, on by default in the Sessions tab, turns it off.
- THE BOARD'S PAGES DRAW THE REDRAWN WORKSTREAM PICTURE. It replaces the station map at three levels: the Overview's workstreams and a workstream's tracks as pills with the waits between them, the parked ones on a row of their own; a track's stations on rails, the critical path a straight spine captioned "critical path, N tasks", finished runs folded into a bead, reviews as diamonds, answers as chips and each session a train with a car per agent. Hover traces what a station waits on and frees; a press selects it and opens a strip with presses to open, answer or resume, and a second press opens it or zooms in. The crumbs, + and -, Back and Copy link keep the view, a line says what changed since your last look, and the wheel scrolls the page, never the level. A board older than this release keeps the band live.
- HOME IN THE PANE DRAWS THE SAME PICTURE AT THE PANE'S WIDTH. Its levels are My track's lines, Whole workstream and the Overview; every station, pill, wait and label is a press that lights grey on hover, the marks use the real favicons, and on the rails the stations draw smaller so the names get the width. A picture past what the pane draws ends in a "+N more on the board" row: a 158-station track at 238 px draws 41. A workstream's loose tasks show as an Inbox N line under its picture, amber when stalled, a fold listing each with its page and wake. The band carries no Overview, which the local board reads only while the pane draws it: on a 72-track board the band is 50 KB against 167 KB and a change settles in 55 ms against 713 ms.
- THE AGENTS SECTION SURVIVES A RELOAD, AND A STOPPED AGENT'S TASK SAYS SO. Each session's agent list rides the mod's store under its own key, kept three days after its last save, and every load rebuilds it against the app's own agent list, so a running agent stays listed through a reload, and a helper rides indented under the agent that started it. When a dispatched agent stops, its task reads "finished: job, landing", or "stopped: job, next leg due" when it handed on, on the board's pages and in the pane, its car leaves the train, and every count, the kickoff and the pane's tips count it apart from running until the session closes the task or sends the next leg; the Overview counts running agents, never a session's task in hand. Against an older board the line reads as it did.
- A PHONE SIGNS IN BY QR CODE. The Settings tab's This PC sub-tab opens with a Sign in a phone card whose press draws a single-use login link as a QR code until it expires, and `askerdo login --qr` prints the same code in half blocks with the link and its expiry. The link goes by an address a phone opens: a bare PC name takes the first private IPv4 the board answers on, never a link-local or virtual adapter's, and a board hosted on this PC, which answers on loopback alone, is refused with the reason. The encoder is vendored (MIT, after Project Nayuki's QR Code generator) and was checked bit for bit against a second encoder over 691 codes. Every login link, the board link from a session included, goes on the address this PC called, keeping a TLS proxy's https and any path it adds.
- A BOARD AND A PC ON DIFFERENT PROTOCOLS REFUSE EACH OTHER PLAINLY. A release that changes what a PC sends or what the board accepts moves the board protocol, now 2. The board refuses a PC on another protocol on every call, and that PC's Needs you band shows one row naming the side to update and how, while the cached question chips under it draw plain, on the band and on Home, with no press and no "Press to answer" line; `askerdo status`, the status row and `/askerdo` say the same, and `board move` refuses a target board on another protocol before it stops anything. A PC on 0.8.15 shows the board's words in its offline row: run `claude plugin update askerdo@askerdo` and start a new session. The join-a-pc card checks a board's version through `/health`, which answers on any protocol. Update the board and every PC in one sitting.
- AN INBOX TASK NAMES ITS WAKE, AND LATER WORK GOES ON A PARKED TRACK. A task on no track carries a wake, the event that brings it back: a track ending, a task completing, a question answered, or a date. `task create`, `task edit`, `track capture` and `track finish` or `track drop` with `--leftovers inbox` take `--wake`; a filing without one is refused with the rule and both ways out (a track parked until its event with `track park --unpark-when`, or a wake to name), and a wake that has already fired is refused with its way out: a filing says to file it again on a track or with a later wake, a task edit to place the task or name a later wake, and a track finish or drop to close the track again with a later wake or drop its open tasks with it. The user's `/askerdo track capture inbox` files 14 days out. `task edit --wake` alone wakes an inbox task again; at the third wake in one inbox stay the board stores none and asks the user on the band to place, keep or drop the task. A handoff's leftover can go on a new parked track that opens on its event (`newTrack` and `unparkWhen`). A due inbox task leads every kickoff on its project: a kickoff asks to place or wake again its own workstream's due tasks and only names another workstream's, and a close must place or wake again its own workstream's and names the others'. The pane's and the board's inbox lists show each task's wake, due tasks first in amber and counted.
- KNOWLEDGE RECORDS POINT A SESSION AT THEIR FILES. A knowledge record takes file globs (`knowledge new --file`, `knowledge supersede --file`, `knowledge edit --add-file` and `--remove-file`), and an edit of a matching file draws one line naming the record with `askerdo show K-n`, and a toast, once per record per loop, through the matcher decisions use. The profile setting `pointers.knowledge`, on by default in the Sessions tab, turns knowledge pointers off; decisions and cards point either way. The conversion writes a path-scoped fact this way, and no board migration is needed.
- CODEX READS THE BOARD'S RULES FROM AGENTS.OVERRIDE.MD. Where a project keeps an AGENTS.md at its git top, the session-start sync on a PC joined to a board writes a git-ignored AGENTS.override.md for Codex: AGENTS.md's text, then the agents' rules in force and the decisions on the project's files and commands, worded with their scope, within Codex's 32 KiB, the sync log counting what it left out. It adds the file to the repo's info/exclude once, rewrites it only when the text differs, leaves an override AskerDo did not write alone and never creates an AGENTS.md. The conversion's handover and undo write it again.
- THE BAND CARRIES NO REVIEW DUE ROW. A review due shows on Home's picture, the Tracks tab, the kickoff, the handoff and the board, never as a band row or count.
- A REVIEW'S COVERS LIST GIVEN BY HAND IS KEPT. A list set with `review covers` and tasks, or the `review_covers` tool, reads only its tasks: the review reopens only for a newer commit on one of them, work outside it waits for the next review, and `coverage` prints "(given)" after it; board migration 014 keeps the mark, and older reviews read it from the activity log. A completed review reopens only for work that began before the review first started with no open review after it, an open review a task waits on by an edge is the station that reads it, a covers row whose record is not a review counts for nothing, and `review covers --none` clears a list. A commit whose subject starts `release:` counts no lines, so a release task is no code task.
- A SETTING'S CHOICES FIT EVERY WIDTH, AND EVERY FOLD IS THE CHEVRON RING. A setting's "What each choice does" boxes take their width from the pane's columns, as many to a row as fit and the rest on new rows (at 730 px three boxes had drawn zero wide, one letter a line), and a text or list setting's field shrinks in a narrow pane, keeping Save and Add on screen at 238 px. A setting's explanation and the Rules tab's line lists open on the blue chevron ring at the end of their first line, as every other fold in the pane does.
- A SETTING'S SAVE AND ADD, AND THE SEARCH'S CLEAR, SIT BESIDE THEIR FIELD. A text or list setting's field and the Settings search field keep their own width while their row grows, so Save, Add and the search's clear sit one gap past the field at every width and Changed only keeps the search row's far end; on a narrow pane the field shrinks before its press wraps. Measured in the rig at 238 to 1400 px: each press 8 px past its field at every width (at 1400 px, against 182 px for Save, 186 px for Add and 937 px for clear before), and nothing past an edge at 238 px.
- A QUESTION CARD'S OPTION RING ANSWERS EVERY PRESS AT ONCE. A press sent again before the ring draws again (a press reported twice, or a second click faster than the redraw) counts once: the ring toggles once and stays. The open rings live in the mod's session state, so a ring press draws again only the question cards under replies and the pane on its Questions tab, never the band, the status row, the pane on another tab or a reply with no card, and a card's ring and the pane's open and shut together. The band, the status row, the pane, a reply's question card and a reply with no card each draw from their own count in the mod's state, and a change writes only the counts of what it changed, so no redraw draws every reply on screen and a reply with no card draws again only when a question lands under it. A board change or an answer draws the band, the status row, the pane and the cards; a strip press draws the band and the pane from a band chip, the cards and the pane from a card; a pane tab switch, a select or zoom on Home's picture, Home's folds and filters and the pane's other views draw the pane alone; a running agent's timer, the meters, the rate rings and the guard chip draw the band, the status row and the pane, never a card; a question placed at a turn's end draws only the reply it lands under; and the Questions tab's minute tick draws the cards only when a card's age would read differently. The harness's times (claude plugin test on the app's engine), with 100 other replies on screen: a board change's last draw ends 34 to 35 ms after it against 113, an answer press's 79 to 81 ms against 214, and a tab switch's or a zoom's 7 to 10 ms against 71 to 83, none of them drawing a reply, against 100 reply draws each before (200 for an answer); an agent running 3 s draws the status row 3 times and no card or reply.

The mod logs each desktop press on a fold ring, a question card's, the pane's or Home's (its key, stale when it was not the key drawn, its toggles and open or shut after), and each redraw by its cause (a board change, an answer, a strip press, a pane tab switch or a zoom), each with every surface it drew in the 2 s after it (band, status row, pane, card, or a reply with no card): the draws, the ms spent drawing and when the first and the last ended. Search filters, counts and ranks in one SQL statement, and `knowledge new`'s near-duplicate check asks for no count: a knowledge write on a 15,000-record board takes 60 ms, against 1435 ms before (19 ms against 158 ms at 3,000). ## 0.8.14 - 2026-11-04

- THE BOARD KNOWS WHICH FINISHED CODE A REVIEW HAS READ. The board keeps the commits each task finished with and the reviews that read them, in two tables (board migration 012) that ride the export, the import and the backups. The mod links every commit a session makes, a subagent's included and with no rules in force, to its task: a task id in the message first, then the agent's dispatched task, then the task in hand, else a guess the readout names; a commit no task owns counts as unowned project work. A handoff write and resume, and `coverage --scan`, link the commits made outside a session whose messages name a task. Only counted source makes a code task: lockfiles, generated files, Markdown, docs, fixtures and binaries never count, and the setting `review.ignore` adds a project's own globs. The verbs are `commit link`, `commit move` (relink by hand, with a reason), `review covers` (set or narrow a review's list) and `coverage <TR-n|WS-n>`, with the session tools `review_covers` and `coverage`.
- THE REVIEW STATION ON A TRACK IS THE GATE. A review task (labelled `review`, or named "Review ...") covers the uncovered code tasks on its track that finished before it started, or, with `--review-scope project` on task create, task edit or a track layout step, every code task in the project since the last project-wide review plus the commits no task owns. A track reads review due once `review.tasks` (5) finished code tasks wait unreviewed: the band draws a review due row whose press opens the Tracks tab at the track, and the kickoff, the handoff and `coverage` say the same. `review.depth` sets how much the board makes of it: `off` nothing, `light` (the default) the nudge, and `full` also reopens a completed review when work it read gains a commit or completes after it, so the tasks waiting on it wait again, and holds `track finish` until a review covers the track's finished code (`--waive "<reason>"` goes ahead and is recorded). A reopened review keeps the covers its change did not outdate, and a commit on a finished track's task reopens nothing there and waits for the next project-wide review. A built-in rule line tells sessions where review stations go: after each wave of parallel lanes, where work touched code another lane or track also touched, once five finished code tasks sit unreviewed, and before anything that ships. Configure offers the depth once on a board, and the Settings tab shows the three review settings under Tests.
- THE STATION MAP DRAWS THE WORK NO REVIEW HAS READ. Finished code tasks no review covers draw as amber beads on their track's rail between stations, on Home's Where we stand and the board's track pages. A review is a diamond: outlined while to do, amber with "N to review" when reopened, and filled grey with "N covered" once done, the beads it covered folded into it; a press on a done review lists what it covered, each a link, closed with the pane's X. A finish held for a review wears an amber padlock, unless a review planned before it is the way through, and the legend names a review mark only when the map draws it. The Tracks tab colours unreviewed done cells amber, draws the padlock on a held tile and reads "review due".
- EVERY NAME THE PANE DRAWS OPENS ITS BOARD PAGE. Track, task, question and decision names and ids in the pane and on the band's cards open their board pages: the Tracks tab's station rows, its tiles' workstream and longest chain (packed whole into two rows), its bottom line and a shut section's names; Home's map, its other workstreams, its wait lines and lines left out; the terminal's line names; the found row's ids; and the track and task hover cards with each wait.
- SETTINGS AND THE BOARD JOIN SURVIVE A PLUGIN UPDATE. This PC's files (config.json with the board address, device token and options, the handoff lists, the project map and the sync log) live in `~/.claude/askerdo/pc/`, which no plugin update, uninstall or marketplace remove reaches. The session start moves an existing plugin data folder there once, renaming config.json into place so a session starting beside it never reads half a file, and leaves the old folder for a downgrade; until the move, and on any copy failure, the old folder is read. A setting or join that a session still on an older AskerDo saves into the old folder reaches `pc/` at the next session start, and a settings copy leaves an unreadable config.json as it is. AskerDo reads the Claude app's folder from `CLAUDE_CONFIG_DIR` when it is set (the output style, settings.json, the plugins and the projects folders), while the store and `pc/` stay in `~/.claude/askerdo`.
- UPDATING A PC IS ONE COMMAND, AND THE APP CAN DO IT ON ITS OWN. `claude plugin update askerdo@askerdo` then a new session updates a PC: the update fetches the marketplace itself (read on Claude Code 2.1.304), every doc that updates a PC says so, and none removes the marketplace. Configure offers the Claude app's auto-update for AskerDo once per PC: a yes turns on `autoUpdate` on the AskerDo entry in `~/.claude/plugins/known_marketplaces.json` (the switch /plugin shows under Marketplaces) and on its `extraKnownMarketplaces` entry in `~/.claude/settings.json` when there is one, keeping every other key, which is the desktop app's way in since it has no /plugin panel. The answer is the per-PC setting `pluginUpdates` (`ask`, `on`, `off`), which the Settings tab also changes. The session start puts the switch back to the saved answer only when the app holds no value, as a marketplace remove and add leaves it, and an on or off set in /plugin becomes the saved answer.
- AN UPDATE REPLACES THE OLD LOCAL SERVER AND BRINGS THE TRAY BACK. A session start replaces an older local server of this store, ending one that will not stop through its stop route by its process id once that process is Node holding the store's port. Session starts racing after an update replace it once: a stop names the version it expects, and a current or newer AskerDo server found instead is kept. A tray closed with Exit comes back at the next session start, and the ping reports the tray as `up`, `closed` or `down`. The local server shuts down, tray included, when its store folder is deleted or its secret minted again: measured, it leaves within one watch tick and the next start brings one up. `askerdo board --restart` stops the local server and starts a fresh one on the same port, the troubleshooting page uses it, and in a session whose copy an update replaced it refuses with the fix to start a new session.
- THE TRAY RUNS FROM ITS OWN COPY IN THE STORE. The tray runs from `~/.claude/askerdo/board/tray/`, one folder per build, so a plugin reinstall never meets a locked exe in the plugin cache: measured, a marketplace remove and same-version reinstall while the tray ran from the cache left 1039 files of the old copy behind, and with the store copy the cache is left whole. - ONE COMMAND SAYS WHAT IS WRONG ON A PC. `askerdo status` checks the store, the saved settings and board join, the board (answering, token, version), this PC's local server, the tray and whether the session runs a copy an update replaced, one line each, every problem with the command or step that fixes it; `--json` gives it as data, and it exits 1 when it lists a problem. A local server that does not answer its ping in time reads as busy, with the fix to check again or run `askerdo board --restart`, and `askerdo board` words that refusal the same way and never stops a server it could not identify. It runs in the asking process, so it judges that copy rather than the local server's. The troubleshooting page starts from it.
